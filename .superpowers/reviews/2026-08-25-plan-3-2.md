| --- | --- | --- | --- | --- |
| 1 run | 27,194 | 10 / **10.0 ms** | 0 / **0.10 ms** | - / **2.0 ms** |

Does not reproduce: **the index column**. The plan never gives the query, and

Two of my three shapes bracket the plan's number, one 17x below it and one 12x

thesis is unaffected: even my cheapest shape is 7.2 s at 30 runs.

Also measured, and it is the finding that changes the plan's scope (C4). The
`0 ms` and `72 ms` above are measured over a store holding **no content samples
at all**, because the sweep declined `classes` for all 543 endpoints. With one
sample per endpoint per run, which is what stage 2b exists to produce:

| history | `endpoint_content.rq` | `endpoint_description.rq` |
| --- | --- | --- |
| 1 run | 1.2 ms | 3.3 ms |
| 7 runs | 115.6 ms | 200.0 ms |
| 30 runs | **6,488.5 ms** | **11,704.3 ms** |

And the design's own thesis, confirmed: a flat scan of a hand-built `current`
graph over the 30-run store is **3.1 ms** for 3,801 rows. A per-endpoint rebuild
of that graph as one SPARQL update over the same store is **43.5 s**.

Two library facts I verified because the plan's crash reasoning rests on them.
`pyoxigraph.Store.update()` documents "Updates are applied in a transactional
manner: either the full operation succeeds, or nothing is written", and it holds
**across `;`-separated operations**: `DROP GRAPH <urn:g>; DROP GRAPH <urn:missing>`
raised and left `<urn:g>` intact. And `?endpoint` substitution reaches a
`DELETE`/`INSERT`/`WHERE` update the same way it reaches a query. See C7.

## Critical

### C1. The activity facts the plan puts in `current` make it a second run for every existing query, and every endpoint page then raises instead of rendering.

> For each endpoint: its measurement rows, its `declarationsRead`, its
> `NotMeasured` facts, its `ContentSample`s, and the activity facts the page
> needs (`prov:generatedAtTime`, `sw:emission`, `sw:finalised`, and that
> endpoint's `sw:completedEndpoint`).

`endpoint_measurements.rq`, `endpoint_content.rq` and `endpoint_description.rq`
all select their run as `GRAPH ?run { ?activity a prov:Activity ;
prov:generatedAtTime ?generatedAt . ... }`, and the newest-run branch's
aggregate is `SELECT (MAX(?anyGeneratedAt)) WHERE { GRAPH ?anyRun { ... } }`,
with no restriction on which graph `?anyRun` may be. A `current` graph that
carries an activity with its type and timestamp is therefore a run, and it
carries the newest timestamp by construction.

Measured, on the committed `run-with-samples.nq` fixture with a `current` graph
added:

```
endpoint_content(store, kadaster)      -> ValueError: ... has 2 runs tied as most
endpoint_measurements(store, kadaster) -> recent (['urn:sparqlwatch:current',
                                          'urn:sparqlwatch:run:2026-08-22T16:00:00Z'])
```

Both readers raise (`web/endpoint_measurements.py:203-208`,
and the same check in `web/endpoint_content.py`), so every endpoint page is a
500 and the RDF representation is a 500 too. Deleting only the
`?activity a prov:Activity` copy from `current` makes all three queries behave
exactly as today, which is the whole difference between a broken store and a
working one, and the plan does not mention it.

Worse, **the suite cannot see this**. Every page, negotiation, measurement and
content test builds its store with `store.load(...)` (`web/tests/conftest.py:41-44`
plus about ten inline `Store(str(tmp_path / "s"))` builds), never through
`load_run()`, so no test store will ever have a `current` graph in it. Task 1
can commit green and break every page in production.

**What the plan should say instead.** State the exact quad shape `current`
holds, and state that no `rdf:type prov:Activity` triple may appear in it: the
run it came from is named by a pointer predicate on the endpoint (say
`sw:currentRun` and `sw:currentGeneratedAt`), not by re-typing an activity in a
second graph. Add a task step that asserts, over a store built by `load_run`,
that `endpoint_content` and `endpoint_description` return exactly what they
returned before `current` existed. And say which conftest fixtures move to
`load_run` so the suite exercises the graph at all.

### C2. "All of the existing tests must pass unchanged" is not achievable, and the only way to make it look achievable defeats the stage.

> **Every claim the page currently makes must survive.** [...] All of the
> existing tests must pass **unchanged**, and if one needs editing, that is a
> behaviour change and it needs explaining rather than accommodating.

Two independent reasons this cannot hold.

1. No test store contains a `current` graph (C1's citation). A query that reads
   `current` returns zero rows for every fixture, so `assessed` is False and the
   page says "no measurement, no decline and no class sample in this store
   mentions ..." for kadaster, ontop, qlever and every other fixture endpoint.
   Dozens of tests fail on the Task 2 commit.
2. `web/tests/test_endpoint_measurements.py:149`
   (`test_the_old_scheme_run_is_still_reachable_once_the_newer_one_is_gone`)
   does `store_new_subjects.remove_graph(NamedNode(NEW_RUN))` and then requires
   the reader to fall back to the older run's verdict. A `current` graph
   maintained only at load time cannot fall back: it still points at the run
   that was just deleted. This test asserts a property `current` genuinely does
   not have.

The hazard is what an implementer does when told the tests must not change: add
"read `current`, and if it says nothing, compute recency the old way". That
passes every test, keeps the 5.8-second path alive for exactly the stores that
matter, and creates two derivations that can disagree with no test able to tell.

**What the plan should say instead.** Name the test changes up front as part of
the task: the fixtures that must be built through `load_run` (which is also the
only way the suite tests the graph the stage adds), and the one test above,
which becomes a test that removing a run graph invalidates `current` (either the
loader refuses to serve, or the removal path updates `current`, which C6 says it
must anyway). Then state the rule that actually matters: no page sentence, no
verdict and no attribution may change, and the negotiation agreement test must
still compare two independent derivations.

### C3. A store built before this stage answers "we know nothing about this endpoint" for every endpoint, and nothing in the plan notices.

The plan has no migration step. After Task 2, a store whose run graphs were
loaded by today's `load_run` has no `current` graph, and the endpoint page for a
fully measured endpoint renders the never-assessed branch:
`web/app.py:851` "no measurement, no decline and no class sample in this store
mentions ...". That is a confident wrong answer about a store that holds eight
verdicts for that endpoint, and it is the state of the only real store this
project has (the preserved 543-endpoint sweep, loaded with the current loader).

`web/app.py:242-285` already refuses to serve a store that is missing or empty,
with a paragraph explaining that answering "nothing measured" out of an empty
store is the failure mode to prevent. That reasoning applies verbatim here.

**What the plan should say instead.** Add to Task 2: `_opened_store` refuses a
store that holds run graphs and no `current` graph, naming the rebuild command
to run. Add a test for it. And say in Task 5's README section that upgrading
requires one rebuild pass.

### C4. The decision to leave the other two queries alone rests on a measurement of a query that matched nothing, and the RDF representation is left slower than the page this stage is fixing.

> The other two queries are not the problem and must not be touched in a panic:
> `endpoint_content.rq` is 0 ms and `endpoint_description.rq` is 72 ms at 30
> runs. Neither is where the time goes.

Both figures reproduce (0.17 ms and 78.9 ms), and both are measured over a store
that holds **zero** content samples, because this sweep declined `classes` for
all 543 endpoints. `endpoint_content.rq` returns 0 rows at every history depth I
tried: the FILTER NOT EXISTS never runs against anything. With one sample per
endpoint per run the same query is **6,488 ms** at 30 runs and
`endpoint_description.rq`, which is the whole RDF representation of the
resource, is **11,704 ms**, twice the page this stage exists to fix. The
per-endpoint recency shape is identical in all three queries, so this is the
same defect in three places, and the measurement only hid two of them.

(Caveat, stated so the number is not oversold: my synthetic store samples every
endpoint in every run, which is the tier-2 steady state only if `classes` runs
at an expensive ceiling every sweep. A rarer expensive sweep makes the growth
slower and the shape identical.)

**What the plan should say instead.** Say that all three read paths compute
recency the same way and all three must move to `current`, and that the content
query's `0 ms` is a query with nothing to match rather than a fast query. If
moving the sample is deliberately deferred, the deferral has to say that the RDF
representation stays O(history) and that one expensive sweep makes it the
slowest thing on the site.

### C5. HTML and RDF stop deriving from the same facts, which is the property stage 3-1 was built to guarantee.

> | `web/queries/endpoint_measurements.rq` | modify | Read `current` instead of
> computing recency, keeping every claim it currently makes. |

`endpoint_description.rq` is not in the plan's File Structure table at all, so
after Task 2 the HTML representation of `/endpoint?url=...` reads `current`
while the RDF representation of the same resource computes recency over the run
graphs. `web/app.py:11-25` states why the two derivations are independent and
why that is a hazard as well as a design; the guarantee that made it safe was
that they read the same quads.

They now diverge whenever `current` is not exactly in step with the run graphs,
which the plan itself says will happen: between the run-graph insert and the
`current` update (separate operations), for as long as an interrupted update
goes unnoticed, and permanently after any of C6's cases. During that window
`curl -H 'Accept: text/turtle'` and a browser get different verdicts for one
URL, and `web/tests/test_negotiation.py` cannot see it, because its fixtures
have no `current` graph at all (C1).

**What the plan should say instead.** Move both representations in the same
commit, or state explicitly that `current` is authoritative for both and that
the CONSTRUCT reads it too. A resource with two representations may not have two
notions of "newest".

### C6. The update rule is monotone-only, so `current` cannot un-say a fact, and the documented recovery does not recover.

> a crash can leave `current` stale or partially updated, which is
> **recoverable by re-loading the run or by rebuilding**, and is detectable by
> the check. What it must never do is leave `current` holding facts that
> contradict a run graph, so update one endpoint at a time and completely.

> After a run's graph is inserted, update `current` for the endpoints that run
> covered.

`load_run.py:9-18` exists for one hazard: the same run IRI seen again with
**changed** content. That hazard is the one the plan's rule cannot handle, in
three shapes:

1. **Re-loading the same run IRI.** Any guard of the form "only advance if the
   incoming run is newer than the run `current` points at" sees a tie, not a
   newer run, and skips the update. So the plan's stated recovery, "recoverable
   by re-loading the run", is exactly the operation that does nothing. If the
   guard is instead "newer or equal", an out-of-order load of an older run is
   still refused correctly, so the fix is cheap, but it has to be written down.
2. **A run graph that shrinks.** Load the complete sweep (543 endpoints), then
   re-load the truncated file the crashed prober left (`load_run` supports this
   deliberately, and `run-truncated.nq` is a committed fixture of the shape).
   The run graph now describes one endpoint; `current` still holds that run's
   facts for 542 others and still names that run as their source. Those are
   facts no run graph contains, attributed to a run that no longer states them:
   a direct breach of the plan's own invariant, and "update `current` for the
   endpoints that run covered" cannot see them, because those endpoints are not
   in the incoming file.
3. **The finished/unfinished flip.** `sw:emission` and `sw:finalised` are
   run-level, and the plan copies them per endpoint. Load a truncated run, then
   the complete one: under the tie in (1) the copy is never refreshed, and the
   page keeps saying "The sweep at T did not finish" about a sweep that did.
   That is one of the two sentences stage 1c-b4 added and the plan promises to
   preserve.

The same shape reaches `current` from a direction the plan does not mention at
all: the spec's own reason for one graph per run is that it "lets a bad run be
dropped wholesale" (spec:110-111), and `remove_graph` is used in the suite
today. Nothing updates `current` when a run graph is dropped.

**What the plan should say instead.** Define the update as "replace what
`current` holds for every endpoint mentioned in the incoming run, and refuse to
advance only when the pointed-at run is strictly newer than the incoming one",
and say that a run graph that shrinks or is dropped requires a rebuild, with the
loader detecting it (an endpoint whose `current` pointer names a run whose graph
no longer mentions that endpoint) rather than leaving it to be found by a
reader. Every one of these three cases deserves a test, and none of them is in
the plan's list; `test_loading_an_older_run_after_a_newer_one_does_not_move_current_backwards`
covers only the easy direction.

### C7. "pyoxigraph 0.5.9 has no transaction API" is false, so the plan accepts a hazard the library does not force on it.

> `load_run()` already documents that dropping a run's graph and inserting it
> are two operations with no transaction available in pyoxigraph 0.5.9, and
> that this is tolerable [...] Updating `current` is a third. State the same
> reasoning and its limit.

`Store.update()` in the installed 0.5.9 documents "Updates are applied in a
transactional manner: either the full operation succeeds, or nothing is written
to the database", and I verified it holds across operations:
`DROP GRAPH <urn:g>; DROP GRAPH <urn:missing>` raised `RuntimeError` and left
`<urn:g>` present. A single
`DELETE { GRAPH <...:current> { ... } } INSERT { ... } WHERE { ... }` update
therefore does exactly what the plan says it needs and cannot do: "update one
endpoint at a time and completely". Substitution works in updates too, so the
endpoint does not have to be interpolated.

So the third operation's hazard is avoidable, and the plan's "state the same
reasoning" propagates a false claim from `load_run.py:30-38` into a new
component instead of correcting it. Without atomicity, a crash between the
delete and the insert leaves an endpoint with **no** facts in `current`, which
after Task 2 renders as "no measurement, no decline and no class sample in this
store mentions ..." for an endpoint the store fully describes: a wrong fact, not
a stale one.

**What the plan should say instead.** One `store.update()` per endpoint, stated
as the mechanism, with the docstring correction to `load_run.py:30-38` in the
same task. Then the crash semantics are honest and short: the run graph and
`current` can be out of step (which C6's detection covers), but no endpoint is
ever half-updated. The same correction is worth noting for the run-graph
replacement itself, where the practical objection is the size of an
`INSERT DATA` body rather than the absence of a transaction.

### C8. The index's headline verdict claim is wrong for four endpoints, and following the Done-when as written publishes a verdict the store contradicts.

> in particular an endpoint that answered nothing has `indeterminate` verdicts,
> **not `absent`**, and the index must not compress that into "dead" or a cross.

> shows `indeterminate` and not `absent` for the 486 that answered nothing

Measured over the run the plan is built on, `sw:metric:availability`:
**57 `verified`, 482 `indeterminate`, 4 `absent`**. 57 + 482 + 4 = 543. The four
are
`https://raw.githubusercontent.com/GVogeler/bookkeeping/master/bookkeeping.ttl`,
`http://sensormeasurement.appspot.com/dataset/naturopathy-dataset`,
`https://purl.org/whonto/onto` and `https://sparql-noipa.mef.gov.it/sparql`.
And `absent` is common on the other metrics of non-responders: `cors` 19,
`cors-preflight` 78, `geo-data` 52, `service-description` 9. So a
"answered nothing" row is routinely a mix of `indeterminate` and `absent` chips,
and there is no such thing as "the 486 that show indeterminate".

**What the plan should say instead.** "Render the verdict the store holds,
never a substitute: 482 endpoints carry `availability` `indeterminate` and 4
carry `absent`, and both are drawn from `verdict_encoding.py` as themselves."
The useful test is not "shows indeterminate" but "for each of these two named
endpoints the chip matches the stored `dqv:value`", plus one that no row
displays a verdict the store does not hold for that endpoint and metric.

### C9. Grouping by "whether the endpoint answered a query" is not the `availability` verdict, and the group heading publishes a wrong fact.

> Group by a **fact**: whether the endpoint answered a query, which is the
> `availability` verdict, then alphabetically within each group. With 57 of 543
> answering, an undivided alphabetical list buries every responder, and grouping
> by a measured fact is not a ranking.

The verdict has at least three values here and the boolean is not any of them.
`prober/src/resolve.rs` records `absent` for a host that **did** answer, with a
2xx and a body that is not a SPARQL result (`liveness_other_body_is_absent`),
which is why one of the four is a `.ttl` file on `raw.githubusercontent.com`,
and it records `indeterminate` for a timeout, a transport error, a DNS failure
or an HTML front end (`a_timeout_is_indeterminate_never_absent`,
`an_html_front_end_is_indeterminate_not_absent`). So a heading of the form
"did not answer" over those four says something false about them, and putting
482 `indeterminate` rows under the same heading turns "we could not determine
this" into a determined negative, which is the one thing the spec's conformance
model exists to prevent ("a number cannot express 'we could not determine
this'", spec:432-434; "`indeterminate` is a required outcome, never a silent
zero", spec:469).

A fourth case has no group at all: an endpoint whose newest run declined every
metric has no `availability` verdict. `run-prober-failed.nq` is a committed
fixture of exactly that (seven `prober-failed` declines and one
`cost-ceiling`), and stage 1c-b3 makes it the normal outcome for a panicked
host group.

**What the plan should say instead.** Group by the `availability` verdict's own
value, one group per value present, each labelled with that state's own label
from `verdict_encoding.py`, plus a final group for endpoints whose newest run
recorded no `availability` verdict, labelled "not measured" and not merged with
anything. Order the groups by the encoding table's order rather than by any
notion of better. State each group's count with its denominator (543 endpoints
in `current`, from the sweep at T), the way stage 1d-a's correction requires.

### C10. `/about` is required to say how to ask to be excluded, and there is no exclusion mechanism, no contact address and no route anywhere in this project.

> and **how to ask to be excluded**. That last is the reason the page exists at
> all from the reader's point of view.

> - [ ] **Step 1: Write the failing tests** (it responds; it names the contact
>   route for exclusion; ...)

I grepped the whole repository for a contact address, a mailto, an exclusion
list, an opt-out or a removal path: there is none, and the plan creates none. The
registry is `prober/registry/lod-cloud.toml`, regenerated from the LOD Cloud
dump by `seed-registry`, and stage 1d-a explicitly deferred the admission policy,
so "nothing yet stops the dead being re-probed" (spec:410). A page that tells a
sysadmin how to be excluded, when nobody reads the channel and the next seed
run re-adds the endpoint, publishes a promise this project cannot keep, to the
543 hosts it has already contacted.

**What the plan should say instead.** Either the stage delivers the mechanism
(one named mailbox that a human reads, plus an `exclusions.toml` that
`registry.rs` subtracts and `seed-registry` preserves, with a test that an
excluded URL never reaches a sweep), or `/about` states the truth: the exclusion
channel is X, requests are handled by hand today, and the automatic list is not
built. The test then asserts the page says what is actually true. A promise is
a claim, and this project's rule about confident wrong answers covers claims
about itself.

## Important

### I1. The index column of the headline table is unreproducible, and the plan publishes it as measured.

The plan gives no query text for "an index-shaped query", and my three
reconstructions bracket its numbers by 17x below and 12x above (see the table at
the top). The same applies to Task 3's "With `current` the query is a flat scan:
28 ms measured over the real store", which describes a graph that does not exist
yet; my flat scan over a hand-built `current` at 30 runs is 3.1 ms. The plan's
own Task 2 Step 1 says "this project has published an unmeasured performance
claim before".

**Should say instead:** include the exact query text for every number in the
table, and say for the 28 ms how the `current` graph it ran against was built.
The argument survives with my 7,249 ms figure; it does not need 256,881 ms.

### I2. "Two orders of magnitude" and "543 times over" are not what the plan's own numbers say.

> The index is worse by two orders of magnitude, because it asks the same
> question 543 times over.

279/10 = 28x, 13,812/303 = 46x, 256,881/5,793 = 44x. One and a half orders, and
a 44x ratio is evidence that it is emphatically *not* 543 independent
executions. Say "roughly 40 times the cost of one endpoint page, because the
recency filter is shared but still quadratic in history".

### I3. The spec quotation does not exist, and the spec's actual wording says something the plan contradicts without saying so.

> **The spec already specified the way out**, in the storage section: "one named
> graph per run plus a derived `current` graph for cheap UI queries".

The Storage section (spec:256-262) says nothing about `current`. The sentence
appears nowhere in the spec. What the spec does say, in Data model (spec:113-116),
is: "A derived `urn:sparqlwatch:current` graph holds **the latest measurement per
(endpoint, metric)** so the UI's common queries stay cheap as history grows. It
is **rebuilt after each run**, never hand-edited."

Both differ from the plan. Per (endpoint, metric) is precisely the blend
`endpoint_measurements.rq:44-52` forbids ("Mixing 'most recent per metric' in
here would let a caller see metric:availability from tonight's run beside
metric:classes from last week's"), so the plan's per-endpoint choice is right and
the spec is wrong. "Rebuilt after each run" is a different mechanism from
"update the endpoints that run covered", and it happens to be immune to C6's
three cases.

**Should say instead:** quote the spec accurately with its section, state that
the per-(endpoint, metric) definition is superseded and why, state that the
incremental update replaces the wholesale rebuild and what that costs (C6), and
have Task 5 correct spec:113-116 rather than only adding "built" beside it.

### I4. The spec requires content negotiation on every resource; the index and `/about` are HTML-only and the plan does not list this as a deferral.

spec:276-278: "**Content negotiation on every resource**: HTML for people, RDF
for machines. A quality-measurement service that is not itself machine-readable
would be self-defeating." `web/app.py:1-9` names that requirement as the reason
the endpoint resource has two representations. The index is a collection
resource and the plan's "Explicitly not in scope" list does not mention it.
Either serve a CONSTRUCT over `current` for `GET /` (cheap, and it is the same
flat scan), or record the deferral with a reason.

### I5. The empty-database request test the spec names is missing from Task 3, and the index is the exact surface the spec names it for.

spec:313-314: "Web: request tests per route, including **the empty-database
case**, which is exactly the bug that 500'd umakadata's dashboard." Task 3's six
tests do not include it, and `web/app.py:242-285` refuses to open an empty
store, so the plan does not say what `GET /` does on a fresh deployment, nor
what it renders for a store with runs but an empty `current` (C3).

### I6. The check and the rebuild are the expensive query, so "detectable by the check" is a safety net that costs what the stage exists to avoid.

> **A derived graph that cannot be verified is a liability.** That is why the
> check exists

A rebuild is the per-endpoint recency computation over all endpoints, which is
the index-shaped query. Measured as one SPARQL update over the 30-run store:
**43.5 s**. The growth is quadratic in history (my index shape: 16 ms, 484 ms,
7,249 ms at 1, 7, 30), so at a year of daily sweeps, which is this stage's own
goal, both the rebuild and the check are tens of minutes to hours. The plan
gives no algorithm.

**Should say instead:** name the cheap rebuild, which is linear: replay the run
graphs in `prov:generatedAtTime` order and apply the same per-endpoint update
each time, so a rebuild costs one pass over the store rather than one
comparison per pair of runs. And give the check a cheap per-endpoint form
(compare `current`'s run pointer for one endpoint against the newest run graph
mentioning it) so drift on one endpoint is detectable without a full rebuild.

### I7. The second unfinished-run condition cannot come from `current` at all, and the plan does not say the store-wide branch stays where it is.

> the unfinished-run sentences added in stage 1c-b4 depend on `sw:emission` and
> `sw:finalised`, so a `current` graph without those cannot serve the page it
> exists to make fast.

True of the first condition only. The second
(`newer_run_did_not_reach_this_endpoint`,
`web/endpoint_measurements.py:135-170`) is about a run that recorded **nothing**
for this endpoint, so a per-endpoint `current` has nothing to say about it by
construction. Its inputs must keep coming from the newest activity in the run
graphs, which is cheap (the query header measures the aggregate at 0.4 ms over
402 runs). If an implementer reads "the page reads `current`" literally, that
sentence silently stops firing on exactly the endpoints a crash affects, which
at 543 endpoints is nearly all of them, and no fixture can catch it (C1).

**Should say instead:** the per-endpoint selection moves to `current`; the
store-wide newest-activity branch stays on the run graphs, unchanged, and
`current` must not be visible to it (C1).

### I8. If `?run` binds to the `current` graph's name, three page claims break at once.

The plan says `current` records "which run those came from and when" but never
says that `?run` and `?generatedAt` in the query's projection must be the
pointed-at run and its timestamp, not the graph being read. Bind them from
`GRAPH ?run` and `measurements.run` becomes `urn:sparqlwatch:current`, whereupon:
`_sample`'s `from_another_sweep` (`web/app.py:570-574`) is true for every
sampled endpoint, so `_provenance` prints "This class sample comes from a
different sweep, at T, and not from the sweep at T" with one timestamp twice;
`newest_run != run` is always true, so the second unfinished-run sentence can
fire on a healthy store; and the page names `urn:sparqlwatch:current` as the
sweep it is reporting.

Also note that both tie checks in `endpoint_measurements.py:203-225` stop
guarding anything once recency comes from a single pointer, and one of them has
its own test (`test_two_runs_tied_as_the_newest_in_the_store_are_refused`,
line 483) whose reasoning is that a silent resolution would attribute one run's
`sw:finalised` to a page naming another. Say which of those checks survives,
where, and what now detects two run graphs sharing a timestamp.

### I9. `current` holds content samples that nothing reads, under a recency rule that would lose them.

The plan puts `ContentSample`s in `current` and leaves `endpoint_content.rq`
untouched, so the samples are dead weight whose only effect is C1's collision.
Worse, the plan's definition ("each endpoint's facts from its newest run")
is the wrong rule for a sample: the newest run that measured an endpoint is
routinely not the newest run that sampled it, because a cheap sweep declines
`classes` and publishes no sample (`store_stale_sample` in conftest is that
fixture, and `_sample`'s docstring calls it "the intended steady state rather
than an edge case"). A `current` built per the plan holds no sample for those
endpoints, so any consumer reading it loses a true observation, which is stage
3-1's Critical returning in a new place.

**Should say instead:** `current` carries two recencies, not one, exactly as the
three read queries do: the measurement-and-decline set from the newest run that
recorded either, and the class sample from the newest run that sampled, each
with its own run pointer and timestamp. Or it carries no samples at all and the
content query keeps its own path, with C4's cost stated.

### I10. Task 1 and Task 2 are not separable, so "both suites green at every commit" cannot hold as ordered.

Task 1 introduces the graph that breaks every page (C1) and the suite cannot see
it (C1), while Task 2 is what makes the graph load-bearing and forces the
fixture changes (C2). Merge them, or make Task 1 write `current` behind a flag
that Task 2 turns on, and say which. As written, the two commits are a green
suite over a broken site.

### I11. The index says nothing about a run that did not finish, and cannot say anything about an endpoint no run has reached.

The endpoint page carries two sentences about unfinished sweeps; the index
carries none, so after a crashed sweep it presents a mixture of runs with no
qualification, and the plan's rule ("a row must not assert more than the
endpoint page would") is satisfied on verdicts and broken on the qualifications
that make them honest. And an endpoint that is in `prober/registry/lod-cloud.toml`
but that no run has ever reached has no facts in `current`, so it is absent from
the index silently: "the index lists all 543" is a property of this one complete
sweep, not of the design.

**Should say instead:** each row names its run and its timestamp (the view model
already carries them, so render them), the page states the newest run in the
store and whether it finished, and the count line says "543 endpoints this
store holds facts for, from sweeps between T1 and T2" rather than naming the
registry.

### I12. `/about` cannot keep the prober's promise until stage 4, and the plan's "it currently 404s" is not what a sysadmin sees.

`prober/src/client.rs:161-164` sends
`sparqlwatch/0.1.0 (+https://sparqlwatch.dev.k8s.semanticscience.org/about)`.
That host has no deployment: stage 4 is the ids3 project-env and it is not
built. So a sysadmin following the User-Agent gets a DNS or connection failure,
not a 404, and adding a local route does not change that. The page is still
worth building now, but the plan should say the promise is kept by stage 4 and
that the route path must match the User-Agent byte for byte, and it should stop
asserting the 404.

Two details for the same task, both verifiable rather than remembered:
`prober/README.md:79-81` gives `--min-gap-ms 2000`, `--retry-after-cap-s 20`,
`--concurrency 4` (hosts, never two requests to one host), and `main.rs:361-364`
pins the first two. Those are the numbers the page must state.

### I13. A row of chips assumes a fixed metric set, and the plan never says what a row does when the run measured a different one.

Today it is seven measured plus one declined, from one metric-definition
revision (`sw:metricDefinitionRevision "fnv1a64:5988db00fe7498fd"`). The spec's
whole premise is that metrics get added and redefined (spec:79-83). A fixed
eight-column grid then either asserts an absence for a metric that run never
asked about, or silently drops a metric a newer run added. Say that a row
renders exactly the metrics its run recorded, and that a metric missing from a
row is drawn as nothing at all rather than as a state.

- **M2.** "**Measure the page's byte size** and report it; if it is beyond a few

  `~/code/sparqlwatch-runs/README.md` keeps runs out of git deliberately.

## Verdict

**Not safe to execute as written.** The measurement that motivates the stage is
sound and reproduces; the conclusion (recency must be paid at load time) is
right. But `current` is specified as a set of fact families rather than as a set
of quads, and every Critical above follows from that: it collides with the three
existing queries (C1), it cannot be reconciled with the suite as it stands (C2,
C3), its update rule cannot un-say a withdrawn fact (C6) while the library it
calls unusable would let it (C7), and the two surfaces it is meant to serve are
left deriving different answers (C4, C5). The index's two honesty claims are
wrong about the data the plan measured (C8, C9), and `/about` is asked to
publish a promise the project has no way to keep (C10).

The fix is not a rewrite of the idea. It is: state `current` as quads with a run
pointer and no activity type; move all three read paths together; make the
update one transactional `store.update()` per endpoint with a written rule for
replacement, shrinkage and removal; render stored verdicts and group by the
verdict's own values; and either build the exclusion path or say plainly that it
is handled by hand.

## New: 2 Critical, 2 Important, 1 Minor

### N1 (Critical). Carrying the run-level facts as predicates on the endpoint IRI puts triples in `current` that appear in no run graph, and the RDF representation then publishes them.

> plus whatever the unfinished-run sentences need carried as predicates on the
> endpoint rather than on an activity.

`sw:emission`, `sw:finalised` and `sw:completedEndpoint` are facts about a run.
Re-subjecting them onto the endpoint produces quads like
`<endpoint> sw:finalised "true"` that no run graph contains, which breaks this
plan's own Global Constraint at `:73` ("nothing in it may contradict a run
graph, and it must be reconstructible from the run graphs alone") and breaks
`endpoint_description.rq`'s stated rule that "every triple below appears
verbatim in some run graph in the store". Since all three read paths now move to
`current` in one commit, the CONSTRUCT has two options and both are wrong: emit
them, and the machine-readable representation asserts that an endpoint was
emitted incrementally and finished, which is meaningless and false; or drop
them, and the RDF loses the inputs to the first unfinished-run sentence while
the HTML keeps them, which is C5 reappearing inside the fix for C5.

**What the plan should say instead.** `current` carries the pointer and nothing
else about the run: `sw:currentRun` and `sw:currentGeneratedAt`. The run-level
facts stay where the prober wrote them, and the query reaches them through the
pointer, `GRAPH ?currentRun { ?activity a prov:Activity ; ... }`, which is a
lookup in one named graph rather than a scan and costs what I7's aggregate
costs. That keeps every triple attributable, keeps the CONSTRUCT's rule intact,
and needs no new vocabulary beyond the two pointers.

### N2 (Critical). I9 is unanswered, and moving the content query onto `current` makes it worse than it was in the first draft: the class sample is lost for the steady-state store.

> holding each endpoint's facts from its newest run and a pointer to which run
> that was

> For each endpoint: its `MeasurementRow` quads, its `declarationsRead`, its
> `NotMeasured` facts, its `ContentSample`s, and two pointer predicates

One pointer, one recency. But the newest run that MEASURED an endpoint is
routinely not the newest run that SAMPLED it: a cheap sweep declines `classes`
and publishes no sample, which `web/app.py:539-549` calls "the intended steady
state rather than an edge case" and `conftest.py`'s `store_stale_sample`
fixtures (16:00 sampled, 18:00 declined). Under this shape `current` holds no
sample for those endpoints, and because `endpoint_content.rq` now reads
`current`, the page stops showing a 59-class sample it shows today. That is the
stage 3-1 Critical inverted: instead of misattributing the sample, the site
loses it.

The golden test will catch this, which is the fixture migration earning its
place, but it will catch it as a red suite in the middle of Task 1 with no
design to fall back on.

**What the plan should say instead.** `current` carries two recencies and two
pointers, exactly as the three queries do today: `sw:currentRun` /
`sw:currentGeneratedAt` for the measurement-and-decline set, and
`sw:currentSampleRun` / `sw:currentSampleGeneratedAt` for the class sample, each
advanced independently by the same strictly-newer rule. Add a test named for
`store_stale_sample`: the sample survives a later sweep that declined
`classes`, and it is still attributed to the sweep that took it.

### N3 (Important). The strictly-newer rule silently resolves the tied-run corruption that the readers currently refuse, and the plan does not say where the refusal goes.

`web/endpoint_measurements.py:188-208` and `endpoint_content.py:91` raise
`ValueError` when two run graphs tie as most recent for one endpoint, because
"picking one of them silently would hide it", and
`test_two_runs_tied_as_the_newest_in_the_store_are_refused` pins the second of
the two checks. Once recency is a pointer written at load time, the per-endpoint
tie cannot be seen by a reader at all, and "refuse to advance only when the
pointed-at run is strictly newer" resolves it by **load order**: whichever tied
run was loaded first wins, silently. So the plan removes a corruption detector
without noticing, and one of its tests survives only because that check happens
to be the store-wide one, which I7 keeps on the run graphs.

**What the plan should say instead.** The loader refuses to update an endpoint
whose incoming run carries the same `prov:generatedAtTime` as the run
`current` already points at, with both run IRIs named, and a test moves the
existing refusal from the reader to the loader. Say explicitly which of the two
reader tie-checks survives (the store-wide one) and that the per-endpoint one
becomes the loader's.

### N4 (Important). The check mode lost its test and its Done-when, and the rebuild algorithm is still unspecified, so the repair path is the 43.5 s shape.

The first draft had "a **check** that reports whether `current` matches what a
rebuild would produce" plus two tests, one of which required it to name the
endpoint that drifted. The rewrite still promises the mode twice, at `:84`
("Gains rebuild and check modes") and `:285`, but there is no test for it in
Task 1's list and no Done-when line, while every other property of `current` got
both. My I6 asked for two concrete things and neither is present: the linear
rebuild (replay the run graphs in `prov:generatedAtTime` order, applying the same
per-endpoint update, one pass over the store instead of one comparison per pair
of runs) and a cheap per-endpoint check (compare one endpoint's `sw:currentRun`
against the newest run graph mentioning it), which is also exactly the mechanism
`:106` already needs for shrink detection.

**What the plan should say instead.** Name the rebuild algorithm, say the check
has a per-endpoint form and a whole-store form and that the shrink detector is
the per-endpoint one, and give the check back its test and its Done-when line.

### N5 (Minor). Two citations do not say what the plan says they say, which is the defect I3 was about.

The spec sentence is at `:113-115`, not `:112-114`. And
`endpoint_measurements.rq:44-48` reads "The run chosen is the one that recorded
ANYTHING for this endpoint, measured or declined, not the newest run per
individual metric: one sweep either measures or declines every metric it applies
to a given endpoint in the same pass"; the plan quotes it as "the newest run per
endpoint... not the newest run per individual metric: one sweep either measured
this endpoint or it did not", which is a paraphrase inside quotation marks. The
argument is right either way, so quote the file.
