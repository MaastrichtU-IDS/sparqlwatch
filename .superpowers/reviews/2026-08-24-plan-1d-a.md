**472 `http` / 76 `https` and nothing else**; **zero** URLs carrying a non-empty
userinfo component; **439** distinct `host_key` groups; largest group

matches. The cost table's three multiplications are right (27 x 3s = 1.4 min,

Does not reproduce:

- **"713 with a `sparql` key"**, and the test comment "970 of the dump's 1683
  datasets have no `sparql` key at all". **All 1683 datasets carry a `sparql`
  key.** 713 carry a non-empty array; 970 carry an **empty array**. See I2.
- **The failure-mode bucketing.** Over the 548 distinct URLs, first-seen status:
  72 OK, 187 an HTTP status, 43 timed out, **16** refused or unreachable,
  **227** naming only a host, and **3** the plan's buckets do not cover. See I4.
- **"it claimed 87 OK"**. 87 is a count over the 725 entries, not the 548 URLs;
  the dump says OK for **72** distinct URLs. See I5.
- **`serde_json` as "the one new dependency"**. It is already a direct
  dependency at `prober/Cargo.toml:12` and already used at `src/client.rs:434`
  and `:736`. See I1.
- **The three endpoints `endpoints.toml` holds today.** None of them, and no URL
  naming any of their three hosts, appears in the dump. See I9.

Two premises the plan does not state, which I verified because its numbers rest
on them: `politeness::host_key` folds only scheme-default ports
(`politeness.rs:138-149`), so 439 is a count of *groups* and not of hostnames
(438); and `emit.rs:642/753/870/1040` skip a fact whose endpoint is not a valid

The measured sweep shape, which the plan needs and does not give. Greedy

## Critical

### C1. The seeded list must not become `prober/endpoints.toml`. Doing so reds CI and makes the default target of every hand-run a multi-hour sweep of 438 strangers.

> | `prober/endpoints.toml` | modify | Becomes the generated 548-candidate list with its provenance header. |

Three concrete consequences, all verified today:

1. `prober/src/registry.rs:319` is
   `let loaded = load_endpoints(include_str!("../endpoints.toml")).unwrap();`
   followed by `assert_eq!(loaded.len(), 3)` and
   `assert_eq!(loaded[0], "https://qlever.dev/api/osm-planet")`. It passes now
   (`cargo test --lib registry::`: 12 passed). Task 2 Step 3 reds it, and
   `.github/workflows/ci.yml` runs `cargo test` on every push, so the Task 2
   commit ships a red `main`.
2. `src/main.rs:20` is `#[arg(long, default_value = "endpoints.toml")]`. After
   Task 2, `cargo run -- --at ...` from `prober/` points at 548 third-party
   hosts and runs for 1.2 to 10.5 hours. That is not a thing a developer should
   be able to do by omitting a flag, and it is the first time this project
   contacts any of those hosts.
3. The spec calls the registry "LOD Cloud dump + YummyData's list, probed once,
   **only responders admitted**" (`:53`) and `registry.rs:1` calls
   `endpoints.toml` "the list of endpoints one sweep probes". 548 unadmitted
   candidates are not that list. The plan itself calls them a "candidate
   registry" everywhere except in the file it writes them to.

**What the plan should say instead.** Write the derived list to a new file, for
example `prober/registry/lod-cloud-2026-06-15.toml`, leave `endpoints.toml` as
the three-endpoint development list it is, and pass the seeded file to the one
measured sweep with an explicit `--endpoints`. Then `registry.rs:319` keeps
meaning what it says, CI stays green, and a Done-when item can read "the seeded
file loads through `registry::load_endpoints` and `endpoints.toml` is
unchanged". Add a Global Constraint that `cargo test` stays green, which the
current list (clippy only) does not cover.

### C2. Because the admission policy is deferred, the first sweep probes `localhost`, `example.org` and ten bare IPs, and publishes permanent assertive facts about them.

> "**The admission policy and the `unreachable-candidates` list.** [...] that
> policy should be written against the first sweep's real numbers rather than
> ahead of them."

Deferring *admission* is sound. Deferring any refusal at all is not. Three of
the 548 candidates are these:

```
http://localhost:3030/Dataset/query
http://www.example.org
http://example.org
```

plus ten bare-IP targets, including `http://47.97.223.173:3030`,
`http://202.45.139.84:10035/catalogs/fao/repositories/agris` and
`http://192.248.64.53:8080/vivo/admin/sparqlquery`.

What goes wrong. `emit.rs` types every endpoint in a chunk as
`dcat:DataService` and publishes seven verdicts plus a `declarationsRead` fact
about it, in a run graph the project never rewrites. So this sweep asserts that
`http://localhost:3030/Dataset/query` is a SPARQL data service, and the read
tier will serve it at `GET /endpoint?url=...`. `localhost` resolves to whatever
the prober's own machine happens to run, so the fact is about the prober, it
differs in every deployment, and two deployments' run graphs will carry
contradictory permanent facts under one IRI. `example.org` and `www.example.org`
are IANA reserved-for-documentation names and were never anybody's endpoint.
The bare IPs point at hosts that may have been reassigned in the years since the
dump; probing an arbitrary high port on a stale IP is not a courtesy this
project should extend uninvited on its first outing.

**What the plan should say instead.** Before Task 3, refuse a small, closed,
justified set at seed time and record each refusal with its reason in the
provenance file: loopback and link-local names and addresses, RFC 1918 and other
non-global addresses, and the RFC 2606 / RFC 6761 reserved names (`example.*`,
`*.invalid`, `*.test`, `*.localhost`). Whether a bare IP is admissible at all is
a real question; take it explicitly rather than by omission. This is not the
deferred admission policy (which is about responders); it is the refusal the
governing rule already implies, since a verdict about `localhost` is a confident
wrong answer no later run can correct.

### C3. Task 3's first question cannot be answered by a `--max-cost cheap` sweep, and answering it from this output would be exactly the wrong answer the project forbids.

> "1. **Is there a named-graph endpoint among the responders?** [...] If a
> responder keeps its data in named graphs, say which, because that is the
> fixture the deferral has been waiting for."

and

> "The four questions the spec's 1d row asks are answered with numbers,
> including whether a named-graph endpoint exists to retire a deferral standing
> since stage 1c-a."

Nothing in this sweep's output can distinguish a named-graph store from a
union-default-graph store. Two reasons, both already written down in this
repository:

- `tests/live_smoke.rs:52-61` says of the shipped content queries: "kadaster
  behaves as a union-default-graph store, so its default graph answers both
  branches on its own and **this test would pass with the `GRAPH` branch
  deleted**." A non-empty binding set is therefore not evidence the `GRAPH`
  branch matched, and the run graph records only the verdict, never which branch
  matched.
- `metrics.toml:116` is `cost = "expensive"` for `classes`, so at
  `--max-cost cheap` one of the two content queries is declined outright and
  publishes `NotMeasured`. "Both content queries" are not run.

So the honest answer available from Task 3 is "this sweep cannot tell", and the
Done-when asserts the deferral is retired. Answering the question needs a probe
that separates the branches (something like
`SELECT ?g WHERE { GRAPH ?g { ?s ?p ?o } } LIMIT 1`, cheap, on responders only),
which is product code, and Task 3 says "This task writes no product code."

**What the plan should say instead.** Either move the named-graph question into
its own small task that adds that probe and states what verdict shape would
retire the deferral, or drop it from this slice and say plainly that a cheap
sweep cannot answer it. Do not leave a Done-when item that can only be satisfied
by over-reading a verdict.

### C4. The plan writes an unverified claim about 114 URLs into the spec as a measured finding, and the survey it cites contradicts it.

> "**Front-end resolution.** The survey found **114 of 548 URLs return HTML**, a
> query console rather than an endpoint."

and Task 4 Step 2: "Name what landed and what the three deferrals are, each with
the reason from this plan's second section."

The survey does not support that reading. `SURVEY.md:31` heads the table "Why
the other **483** URLs failed, first attempt", but its thirteen rows sum to
**548**, not 483, so the 114 row does not come from the same probe as the rest;
`SURVEY.md:227` records that the 114 comes from `harvest_sd.py`, "queryless GET
of all 548 URLs". And `SURVEY.md:217` says so outright: "114 URLs returned 200 +
HTML; **some of those hosts do have a working endpoint**." A SPARQL endpoint that
answers a queryless `GET` with its own HTML query form is behaving normally;
that is what Virtuoso, Fuseki and YASGUI-fronted deployments do. "Returns HTML
to a queryless GET" is therefore not evidence that a URL is a console rather
than an endpoint, and this project's own `service-description` metric exists
precisely because a queryless GET is an ambiguous signal.

Recording "114 of 548 are a query console rather than an endpoint" in the spec
publishes a wrong fact into the project's binding document. The spec already
carries the same claim at `:531-534`, so the plan is repeating it rather than
inventing it, which makes correcting it more valuable, not less.

There is a second problem in the same deferral. The spec at `:531` calls
front-end resolution one of "**Two resolution steps [that] are mandatory before
admission**". Deferring a step the spec calls mandatory is allowed (this slice
admits nobody, so nothing is admitted without it), but it must be recorded as
"the spec calls this mandatory before admission and this slice admits nobody",
not as a fresh measured justification.

**What the plan should say instead.** "The survey's queryless GET of all 548
URLs got HTML from 114 of them (`SURVEY.md:45`, `:227`). That is a hint, not a
classification: an endpoint answering a queryless GET with its own query form is
ordinary, and `SURVEY.md:217` notes some of those hosts do have a working
endpoint. Telling a front-end from an endpoint needs a probe designed for the
question, which is why it gets its own plan. The spec calls this step mandatory
before admission (`:531`); this slice admits nobody, so nothing is admitted
without it."

### C5. Task 3 Step 1 is an unbounded, un-resumable, unrepeated multi-hour run, and it is this project's first contact with 438 hosts.

> "`--max-cost cheap`, `--concurrency 4`, against the 548-candidate registry,
> with `--at` recorded. **Expect it to take a long time and let it.**"

Four things go wrong together.

1. **Nobody knows how long, and the plan does not say.** Measured makespan at
   `--concurrency 4` is **1.2 h, 4.5 h or 10.5 h** depending entirely on what
   the 227 unknown-cause candidates cost (table above). The plan identifies that
   the 227 are the unknown, then declines to bound the run they price.
2. **A killed run yields nothing.** `write.rs:127` opens the partial with
   `.create_new(true)` and `main.rs` refuses a rerun that shares an `--at`
   ("`{} already exists, so an earlier run of {at} did not finish`",
   `write.rs:131`). There is no resume. A sweep killed at hour 6, by a laptop
   lid, a `SIGINT`, a DHCP change or an OOM, cannot be continued; a fresh `--at`
   restarts at endpoint 1. "Let it" is a plan for losing a working day and
   producing no measurement.
3. **One uncontrolled run is not a measurement of the four questions.** Three
   of the four (cost distribution, redirect gate queuing, writer cost) are
   sensitive to the machine, the link and the time of day, and one run gives no
   variance and no way for a later reader to tell a network hiccup from an
   endpoint. The plan's Task 3 header says the numbers are "the input to every
   later 1d decision", which raises the bar rather than lowering it.
4. **The politeness reasoning covers each request and never covers doing this
   at all.** The per-host gate, the 2s gap, the honest User-Agent and
   `--concurrency 4` are all in place and all about individual requests. Nothing
   in the plan asks whether the right first contact with 438 strangers is
   3,836 requests in one unannounced burst, and 476 of the 548 are candidates
   the dump itself already reports as failing.

**What the plan should say instead.** Stage the first contact and say what each
stage is for:

- Step 1a: the 72 candidates the dump reports OK, on their own. Roughly 20
  minutes, exercises the responder path, and produces the responder list every
  later question needs. If the writer, the loader or the read tier break at
  scale, they break here cheaply.
- Step 1b: a bounded slice of the rest (say the 100 largest-group candidates,
  which is where the sequential-group risk lives), with a stated wall-clock cap
  and an explicit abort criterion.
- Step 1c: the full list, only once 1a and 1b have held, with the expected
  duration range stated up front (1.2 to 10.5 h), the `--at` chosen in advance,
  and a stated policy for a killed run (there is no resume, so say that the
  partial is loaded for what it covers and the sweep is restarted under a new
  `--at`, or add resume and call that its own task).
- Record the requests-per-host total (7 per endpoint, plus one gated request per
  redirect hop) and say why that load is defensible against a stranger who never
  asked to be probed.

## Important

### I1. `serde_json` is not a new dependency, is not transitive, and `Cargo.toml` has no comments to imitate.

> "`serde_json` is the one new dependency and Task 1 argues for it."
> "[...] adding `serde_json`, which is already in the tree transitively and is
> the ecosystem's default. Say that in `Cargo.toml`'s comment, the way the
> existing pins are justified."

`prober/Cargo.toml:12` already reads `serde_json = "1"` as a **direct**
dependency, and `src/client.rs:434` and `:736` already use it to parse SPARQL
JSON results. So it is neither new nor transitive (it is also a transitive
dev-dependency through `wiremock` and `assert-json-diff`, which is the
irrelevant half). And `prober/Cargo.toml` contains **zero comments**, so
"the way the existing pins are justified" describes nothing.

Global Constraints should read "no new dependencies", Task 1's dependency
argument should be deleted, and `Cargo.toml` should be modified only to add the
second `[[bin]]`. A plan that argues for a dependency it already has is a plan
that did not read the manifest, which matters because the Global Constraints
make "one new dependency, no others" a checkable rule.

### I2. All 1683 datasets carry a `sparql` key, so one named test tests a shape the dump never produces and the shape it always produces is untested.

> `fn a_dataset_with_no_sparql_key_contributes_nothing() { // 970 of the dump's
> 1683 datasets have no `sparql` key at all. }`

Measured: `sparql` is present on **1683 of 1683**; its value is a JSON array in
every case; **970 arrays are empty**. So the comment is false, and the fixture
instruction that follows cannot be carried out:

> "Cut the fixture from the real dump: a handful of datasets covering a dataset
> with no `sparql` key [...]"

There is no such dataset to cut. Both shapes deserve a test (a missing key is
cheap insurance against a future dump), but the plan must say which one the real
dump produces, or the fixture will be hand-fabricated while the reviewer of the
implementation believes it was cut from the dump. Rename to
`a_dataset_with_an_empty_sparql_array_contributes_nothing` with the true count
(970 of 1683), and keep the missing-key case as a separate, explicitly synthetic
test.

### I3. No entry has a blank `access_url` either, and the "trim it" rule contradicts the plan's own verbatim constraint.

> `fn an_empty_or_whitespace_access_url_is_not_a_candidate() {}`
> "[...] for each entry in its `sparql` array, take `access_url`, trim it, and
> keep it if non-empty."

Measured: every one of the 725 entries has an `access_url`, all 725 are strings,
and **none** is empty or whitespace-only. Trimming changes nothing on this dump.
That matters because the plan's own Global Constraints say:

> "**The endpoint string is used verbatim.** No normalisation, no lowercasing, no
> trailing-slash stripping."

Trimming is a normalisation, and it is the one that interacts with
`registry::dedupe`'s deliberate exact-string comparison: `" http://x/sparql"`
and `"http://x/sparql"` are one candidate after trimming and two before. Since
the case does not arise, take the decision explicitly rather than by accident:
either state that trimming is the single permitted normalisation and why it does
not weaken `dedupe`, or refuse a whitespace-bearing value loudly and name it in
the summary. Either way, say the fixture case is synthetic.

### I4. The failure-mode bucketing does not reproduce, and three statuses fall in no bucket.

> "The dump's own failure modes, bucketed: 72 OK, 187 an HTTP status (fast), 17
> refused or unreachable (fast), **43 timed out (slow)**, and **229 naming only a
> host with no cause recorded**"

Re-derived over the 548 distinct URLs on first-seen status: 72 OK (agrees), 187
an HTTP status (agrees, `FAIL (nnn)` for a three-digit code), 43 timed out
(agrees, `Connect timed out` 42 plus `Read timed out` 1 at first-seen), **16**
refused or unreachable (`Connection refused` and `Host is unreachable`), **227**

`FAIL (Connection reset)`, `FAIL (Unexpected end of file from server)`,
`FAIL (test-svu)`. The plan's numbers sum to 548 because two of them absorbed
the leftovers silently.

The plan's own instruction applies to the plan: "If your numbers differ, stop and
tell me". State the bucket rule (what string patterns go where) alongside the
counts, so the numbers are reproducible rather than asserted, and give the three
leftovers a home or a row of their own. The downstream conclusion, "between 43
and 272 endpoints may be slow", becomes 43 to 270 and is unaffected.

### I5. "87 OK" is a count over 725 entries compared against a count over 548 URLs.

> "**Do not** consult the dump's own `status` field to filter: it claimed 87 OK
> where the survey's own probing found 65 live, so it is stale"

and the test comment "(87 OK against the survey's 65 live)".

`SURVEY.md:25` is "The LOD Cloud's own `status` field claimed 87 endpoints OK and
638 FAIL", and 87 + 638 = **725**, the entry count. Over the 548 distinct URLs

The conclusion (the `status` field must not gate a candidate) is right and well

### I6. The cost table is right about arithmetic and wrong about mechanism, and it omits the total.

> | 210s (seven probes each burning the 30s request budget) | about 94 minutes |
> | 600s (the endpoint budget) | 270 minutes |

Row 2 omits the gaps. `DEFAULT_MIN_GAP` is 2s and the seven probes to one
endpoint are serialised behind the per-host gate, so seven full request budgets
plus six gaps is **222s**, and the group is 100 minutes, not 94.

Row 3's 600s is reachable, but not by the mechanism the table implies. Seven
requests cannot exceed 222s, so the endpoint budget is not reached by "seven
probes". What reaches it is a redirect chain: `client.rs:49-54` and `:294-353`
resolve up to ten hops and take the per-host gate for **every** hop, so a
metric on a redirecting endpoint can cost ten gated requests, and 118 of the 548
carry a 3xx status in the dump. Say that, because it is also the mechanism
Task 3's question 2 is about, and because `README.md:227` attributes 600s to a
"black-holed endpoint", which cannot reach it either.

And the table prices one group while the stage is about a sweep. Add the sweep
totals (1.2 / 4.5 / 10.5 h at `--concurrency 4`, from the table at the top of
this review) so the reader of Task 3 knows what "a long time" is.

### I7. The stated risk is real for the group and wrong about the sweep.

> "**A host group runs sequentially, so one dead host with many endpoints can
> dominate the sweep.** [...] `--concurrency` cannot help"
> "So between 43 and 272 endpoints may be slow, and where they sit relative to
> the host groups decides the sweep."

The first sentence is true of the group. The last is not true of the sweep.
**407 of the 439 groups hold exactly one endpoint**, and only 11 groups hold
more than five. At `--concurrency 4` the talis group is 6 minutes of a 1.2 h
makespan in the fast regime and 4.5 h of a 10.5 h makespan in the slow one. So
the largest group is the floor only at the pessimistic end; across most of the
range what decides the sweep is the **aggregate serial work spread over 407
singleton groups**, and `--concurrency` reduces exactly that, linearly, until
the talis group becomes the floor.

This matters because it changes the next slice. If the 227 fail fast, the answer
is a higher `--concurrency` plus the admission policy, and a per-host breaker
buys almost nothing. If they burn the endpoint budget, the breaker is the whole
game. The plan should say both regimes and what number distinguishes them, which
is exactly the "measure first" discipline it invokes.

### I10. Task 3 asks for two numbers the shipped code cannot produce, while declaring it writes no code.

> "This task writes no product code."
> "2. **How often does a cross-host redirect actually queue at another host's
> gate?**"
> "4. **Do 548 chunks per sweep want an `fsync`?** Report the writer's cost as a
> share of the sweep."

Question 2 needs the time a request spent waiting on a gate it did not own.
Nothing measures that. `client.rs:353` logs
`debug!(from = %target, to = %next, "re-issuing the request at a redirect target")`,
which gives you a hop pair and no wait time, and the plan does not even say to
run at `RUST_LOG=debug` or to capture the log, so as written the sweep produces
nothing to count. Counting cross-host redirects is achievable from that log;
"how often it queues at another host's gate" is not.

Question 4 answers itself without a sweep. `run-with-samples.nq` is under 30 KB
for two endpoints and this sweep declines the one expensive sampling metric, so
548 chunks are on the order of tens of kilobytes total against a run measured in
hours: 548 `fsync` calls at even 10 ms each is under 6 seconds of a 1.2 h floor.
"Affordable" is arithmetic. And affordability is not the question 1c-b4 left
open: the spec's 1c-b4 row says "a power loss can still lose a flushed chunk, and
the zeroed tail such a loss can leave is refused whole rather than rescued", and
the plan's own C1-era lineage notes that an `fsync` per chunk still does not
cover the directory entry for the final rename. That is a durability-sufficiency
question, not a cost one.

Say plainly which questions this slice can answer with no code (the cost
distribution, and a count of cross-host redirects from the debug log), which need
instrumentation and therefore a task (gate wait time), and which are settled by
arithmetic rather than by a sweep (`fsync` affordability). Then state what the

### I11. "The four questions the spec's 1d row asks" misattributes one and drops one.

| fast fraction of the 227 | projected makespan |
| --- | --- |
| 0.00 | 4.5 h |
| 0.25 | 3.5 h |
| 0.50 | 2.9 h |
| 0.75 | 2.1 h |
| 1.00 | 1.2 h |
