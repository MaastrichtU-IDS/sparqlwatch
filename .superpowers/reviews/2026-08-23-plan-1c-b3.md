## Critical

### C1. Task 2 is not a pure refactor. It destroys every partial result on endpoint-budget expiry, and publishes a false `declarationsRead` fact.

> "This is a pure refactor with no behaviour change. It exists because a future that
> writes through `&mut Vec` borrowed from its caller cannot be moved into a task"

> Produces: `struct EndpointSweep { rows: Vec<MeasurementRow>, declarations_read: bool, content_samples: Vec<ContentSample> }`, and `async fn probe_endpoint(...) -> EndpointSweep`

The three `&mut` parameters are not an accident of style; they are the mechanism that
makes results survive cancellation, and the code says so at `lib.rs:131-140`:

> "One endpoint's metrics, in definition order, appending as it goes so a caller that
> cancels this future can still see how far it got. [...] `run_sweep` wraps this whole
> function in the endpoint budget, and a cancelled future returns nothing, so a fact
> that depended on this call's return value would simply be lost whenever the budget
> expired before the fetch finished."

`run_sweep` wraps `probe_endpoint` in `budget.with_endpoint_budget(...)`, which is
`tokio::time::timeout`, which **drops** the future on expiry. A future that returns
its results returns nothing when dropped. Concretely, for any endpoint whose 600s
budget expires (the normal case for a slow or black-holed endpoint, which is why the
third budget level exists at all):

- every `MeasurementRow` already measured is lost. The expiry fill at `lib.rs:102`
  then reads `rows.len() == 0` and writes `Indeterminate` rows for **all** metrics,
  replacing real verdicts and their `elapsedMs` values with nothing.
- every `ContentSample` already collected is lost. Today `probe_endpoint` pushes
  straight into `run_sweep`'s run-level vec (`lib.rs:91`, `:286`), so partial samples
  survive.
- `declarations_read` reverts to `false` for an endpoint whose description was
  fetched and parsed. That is the exact dishonest fact `lib.rs:37-45` exists to
  prevent, and `prober/tests/end_to_end.rs:577`
  (`a_budget_expiry_after_the_fetch_still_publishes_declarations_read`) fails on it.
  Its own docstring names this mistake: "Moving that assignment to after the metric
  loop used to cause zero test failures, while making this endpoint publish
  `declarationsRead = false` about a description we had just read."

The plan's diagnosis is also wrong, and that matters because it points at the wrong
fix. The obstacle to `tokio::spawn` is not `&mut`, it is the **owner** of the borrow.
An accumulator owned by the spawned task is `'static`:

```rust
let mut acc = EndpointSweep::default();
let outcome = budget.with_endpoint_budget(
    probe_endpoint(&ep, &defs, &client, budget, &mut acc)).await;
(i, acc, outcome)   // acc holds whatever was written before the drop
```

**What the plan should say instead.** Keep `probe_endpoint`'s side-effecting shape and
move the accumulator's ownership into the per-endpoint unit of work. State that the
refactor is "move the accumulator, not the writes", state that cancellation-safety is
the invariant being preserved, and name `end_to_end.rs:577` as the test that pins it.
Delete the sentence "This is a pure refactor with no behaviour change" and replace it
with "this refactor is behaviour-preserving only if partial results still survive a
dropped future; here is why".

### C2. A panicked endpoint task leaves that endpoint with no facts at all, which is the exact spec violation the superseded plan was killed for.

> "A `JoinError` (a panicked task) is logged at `error` with the endpoint, counted,
> and the other endpoints are kept: losing 547 endpoints to one panic is the failure
> stage 1c-b4 exists to prevent"

Two defects, one of them permanent in the graph.

First, the mechanics do not work as written. `JoinSet::join_next` yields
`Result<(usize, EndpointSweep), JoinError>`; on the `Err` arm **you do not have `i`
and you do not have the endpoint URL**, so it cannot be "logged at `error` with the
endpoint". `JoinError::id()` gives a `tokio::task::Id`, which is only useful if the
spawn loop records `AbortHandle::id() -> (i, endpoint)` in a side map. The plan does
not mention that machinery.

Second, and worse: keeping the other endpoints means the panicked endpoint
contributes **zero quads**. No measurement rows, no `NotMeasured` facts, no
`declarationsRead`. That breaks the one-row-per-(endpoint, metric) invariant that
`lib.rs:26-27` states and that `end_to_end.rs:514` pins, and it is decisive defect 3
from the superseded plan's own header, restated:

> "'A metric above the cost ceiling produces no row' contradicts the binding spec,
> which twice requires recording `not measured` rather than a misleading zero [...]
> a missing row is indistinguishable from a metric that never existed in that
> revision."

The spec's tier table (line 168) says `not measured, never a zero`, and line 173:
"reporting `not measured` is the truth". A silently absent endpoint is worse than a
zero: `web/queries/endpoint_measurements.rq` picks "the most recent run that recorded
anything for this endpoint", so the vanished endpoint keeps showing **last night's**
verdicts as current, with nothing anywhere saying this run failed on it.

**What the plan should say instead.** Record the `(i, endpoint)` mapping at spawn.
On a `JoinError`, fill slot `i` with a complete `EndpointSweep` of `Indeterminate`
rows built through `resolve(def, Declared { claimed: false }, Err(Expired))` (the same
route the expiry path already uses, so judgement stays in `resolve.rs`) plus
`declarations_read: false`, and log at `error`. Alternatively add a
`NotMeasuredReason::ProberFailed` and emit one `NotMeasured` per metric. Either way,
say explicitly that a panicked endpoint must still occupy its slot with facts, and
add a test asserting the run holds one row per (endpoint, metric) when one endpoint's
task panics.

### C3. The subject's uniqueness has no guard at the point of use, and a collision is a node with two contradictory `dqv:value` objects that can never be corrected.

> "**It is injective, provably rather than probabilistically.** An encoded endpoint
> contains no `:` at all, and a validated metric id contains no `:`, so the last two
> colon-separated fields are unambiguous however many colons the run timestamp holds."

The injectivity argument is sound as far as it goes, and I checked the boundary cases
the brief raises. Right-splitting is unambiguous even with a colon-bearing run id
(`run="r", ep="x"` gives `...:r:x:cors`; `run="r:x", ep=""` gives `...:r:x::cors`);
percent-encoding is injective on strings, so `x:y` and `x%3Ay` stay distinct;
non-ASCII and spaces encode to `%XX` over UTF-8 bytes and produce a valid IRI; and an
empty metric id is excluded by `[a-z0-9][a-z0-9-]*` requiring at least one character.
The proposed regex accepts all eight shipped ids in `prober/metrics.toml`
(`availability`, `cors`, `cors-preflight`, `geo-functions`, `geo-data`,
`service-description`, `has-classes`, `classes`), so nothing breaks.

The defect is that injectivity is a property of the **function** and the plan never
addresses the property of the **input**: nothing guarantees that two entries of
`rows` do not carry the same `(endpoint, metric_id)`. Under today's running index they
would get two distinct subjects. Under the new scheme they land on one node, and if
their verdicts differ that node carries two `dqv:value` literals: "verified" and
"absent" on one measurement. That is the governing rule broken in the most permanent
way available, because a run graph is append-only and the plan itself argues "a
published identifier can never be corrected".

The only thing standing between this and the graph is `registry::dedupe`, in a
different module, whose own doc justifies itself on `declarationsRead` and says
nothing about subjects. `run_sweep` is `pub` and does not dedupe; `emit_nquads` is
`pub` and does not check. The same asymmetry applies to the no-colon invariant:
`subject_iri` returns `anyhow::Result` and could check its own precondition, but the
plan puts the check two modules away in `metrics.rs` and has `subject_iri` trust it.
It is also worth knowing the failure is not silent downstream: `web/load_run.py`
computes `expected = len(set(quads))` so the load succeeds, but the endpoint page
then refuses a duplicated row (commit 972dad3), so a collision surfaces as an
endpoint whose page will not render.

**What the plan should say instead.** (a) Have `subject_iri` reject a `metric_id`
that is not `[a-z0-9][a-z0-9-]*`, so the invariant is enforced where it is relied on
and not only where it is convenient; better, introduce a validated `MetricId` newtype
so an unvalidated id cannot be constructed. (b) Have `emit_nquads` detect a repeated
subject and refuse the whole emission (or drop the duplicate with a warning, matching
the existing junk-endpoint handling) rather than silently merging. (c) Add a test that
two rows with the same (endpoint, metric) do not produce one node with two
`dqv:value` objects. (d) Add a sentence to `registry.rs`'s dedupe doc saying that the
subject scheme now depends on it, so the two cannot drift apart.

### C4. `--concurrency` is spent from the per-host gap, so an unvalidated value silently turns healthy endpoints into `indeterminate`. This is the defect `validate_min_gap` already exists to refuse.

> "Validate `>= 1` and reject 0 with a clear message: 0 would mean a sweep that
> measures nothing while looking like it ran."

> "One request in flight per host, and the min gap measured from release. The
> politeness gate already guarantees this and its per-host lock is not reentrant"

`>= 1` is not the constraint that matters. `Politeness::acquire` sleeps the min gap
**while holding the per-host lock** (`politeness.rs`, the `acquire` body), and the
gate is taken per outbound request in `gated_hop`. So when `k` endpoints on one host
are in flight, each of them waits up to `(k-1) x min_gap` extra for the lock, on top
of its own gap, and all of that is spent **inside the 60s metric budget**. Working
the same arithmetic `main.rs:127-159` already does for `--min-gap-ms`:

    (concurrency - 1) x min_gap + min_gap + request budget < metric budget

At the plan's default: `3 x 2 + 2 + 30 = 38 < 60`. Safe, and the plan should say so,
because right now the default's safety is an accident nobody has written down. At
`--concurrency 16` with the default gap: `30 + 2 + 30 = 62 > 60`, so on any
host-clustered stretch of the registry every metric burns its whole budget and
reports `indeterminate`. That is verbatim the failure `validate_min_gap`'s doc comment
says must be refused up front:

> "A gap that leaves no room for one request under the metric budget turns a healthy
> endpoint into a row set of `indeterminate` verdicts [...] Nothing warns when that
> happens, because `run_sweep` warns on an expired ENDPOINT budget and a cancelled
> metric budget is silent, so the operator would read the run as a finding about the
> endpoints."

The project has already paid for this lesson once. Adding a second flag that spends
the same budget, with only a `>= 1` check, reintroduces it.

**What the plan should say instead.** Validate `--concurrency` against the same
relation as the gap, in a `validate_concurrency(concurrency, min_gap, budget)` beside
`validate_min_gap`, refusing at startup with a message naming both numbers and the
budget they have to fit inside. Write the default's arithmetic into the flag's doc
comment (`3 x 2 + 2 + 30 = 38 < 60`) the way the retry cap's is written. And state in
the plan that concurrency and `--min-gap-ms` are not independent knobs.

## Important

### I1. Task 3 bundles eight concerns, and one of them belongs in Task 2.

Task 3 contains: the `run_sweep` signature change, `Arc<Client>`, the `Semaphore`, the
`JoinSet`, the slot reassembly fold, the **extraction of `probe_one_endpoint`**, panic
handling and counting, the CLI flag with validation, and the exit status. The
extraction is explicitly a refactor:

> "Write `probe_one_endpoint` as the piece that wraps `probe_endpoint` with the
> endpoint budget and the budget-expiry fill from `lib.rs:94-111`, so the task body
> stays small and the expiry logic keeps one home."

That is behaviour-preserving and it is precisely what Task 2 is for. Doing it inside
the concurrency commit means any behaviour change in the commit is unattributable
between the refactor and the concurrency. Move it to Task 2 (where it composes
naturally with C1's fix, since the accumulator and the expiry fill then live in one
function), and leave Task 3 as: signature, semaphore, JoinSet, fold, flag, exit.

### I2. The fold must reassemble all four fact lists by slot. The plan names two.

> "collect into Vec<Option<_>> indexed by i, then flatten in order, appending the
> declined facts per endpoint exactly as the sequential loop did."

`Sweep` has four lists: `rows`, `declarations_read`, `not_measured`, `content_samples`
(`lib.rs:55-67`). The sketch mentions rows and declined facts. If `declarations_read`
or `content_samples` are pushed in completion order, the emitted file's order changes
and the plan's own order guarantee is violated for two of the four fact kinds. Name
all four, and say that the slot is the unit: one slot yields one endpoint's rows, its
one `declarationsRead`, its samples, and its declined facts, appended in that order.

### I3. `a_failed_endpoint_task_does_not_discard_the_others` cannot be written as specified.

> "Unit test on the fold that turns task results into a Sweep: feed it one `Err`
> beside two `Ok` results"

`tokio::task::JoinError` has no public constructor. A test cannot construct one, so a
fold typed over `Result<_, JoinError>` is not unit-testable at all. Specify the fold
as a free function over the already-normalised slots, for example
`fn assemble(slots: Vec<Option<EndpointSweep>>, endpoints: &[String], defs: &[MetricDef], declined: &[MetricDef]) -> (Sweep, usize)`, with the `JoinError` translated to
`None` (or to C2's filled-in Indeterminate sweep) at the `join_next` site. Then the
test feeds `[Some, None, Some]` and asserts both survivors are present in input order
and the count is 1.

### I4. Task 2's "green before and green after" test does not pin the behaviour the refactor threatens.

> "The behaviour to pin is that the refactor changes nothing. Write a test that sweeps
> a wiremock endpoint and asserts the full `Sweep` contents"

> "A refactor's test is a before-and-after equality, so it must be green before the
> change and green after."

A test that is green before and after is only meaningful if it would go red under the
plausible ways the refactor can go wrong. A healthy wiremock endpoint exercises the
success path, where returning results and writing through `&mut` are indistinguishable.
The behaviour actually at risk is cancellation mid-endpoint (C1), and the plan's test
would have stayed green through the whole data-loss regression. This project has
shipped five such tests already.

Two existing tests do carry the load: `end_to_end.rs:514`
(`an_endpoint_budget_expiry_still_yields_one_row_per_metric`) and `:577`
(`a_budget_expiry_after_the_fetch_still_publishes_declarations_read`). Note that only
the second one actually fails under the return-value refactor: in the first, all three
rows are `Indeterminate` either way, so it passes while the loss happens. The plan
should name both, say which one is load-bearing and why, and add the missing case:
an endpoint where some metrics complete and then the budget expires must keep the
completed verdicts and their `elapsedMs`, plus any sample already collected. Nothing
in the suite covers that today.

### I5. Both "prove nothing else changed" steps specify a comparison that cannot succeed.

> "Run the prober against the committed `endpoints.toml` twice if the network allows
> [...] and compare old output to new: the multiset of (predicate, object) pairs must
> be identical, and the count of quads must be identical."

The plan states four paragraphs earlier that `elapsedMs` is a wall-clock measurement,
so the `(predicate, object)` multiset of two live runs is never identical. Worse, live
verdicts flip between runs (a 30s request budget against `qlever.dev/api/osm-planet`
is exactly the borderline case `run-with-samples.nq` records at 30003 ms), and a
flipped verdict adds or removes a whole `ContentSample` node, so the quad count moves
too. The same applies to Task 3 Step 4:

> "confirm the two outputs have the same quad count and the same subjects"

at `--concurrency 4` versus `1`. An executor running these will see a failure that is
not a defect, and will weaken the check until it passes while reporting the Done
criterion "proven by comparison rather than by inspection" as met.

**What it should say instead.** Do the comparison where it is actually decidable:
build one synthesized `Sweep` fixture in memory, emit it with the old subject code and
with the new, and assert the `(predicate, object)` multisets and the quad counts are
equal and only the subjects differ. That is a real proof, it belongs in
`emit.rs`'s tests, it runs in CI, and it needs no network. Keep the live run as a
smoke check with no equality claim attached.

### I6. `two_endpoints_actually_overlap` has no body, a wrong number in its comment, and the shape that passes on a sequential implementation.

> "Two 300ms endpoints at concurrency 2 must take well under the 600ms a sequential
> sweep needs. Assert generously (a single bound, no upper-and-lower sandwich): this
> is a wall-clock test and CI is not a quiet machine."

600ms is wrong. A cheap sweep is seven requests per endpoint (`README.md:153-156`), not
one, so two endpoints at 300ms per response cost roughly 4.2s sequentially, not 600ms,
and the plan's threshold is off by a factor of seven in the direction that makes the
assertion vacuous. And "assert generously" plus "a single bound" is exactly the
combination that passes on a sequential implementation: the bound has to be loose for
CI, and a loose bound on a 4.2s baseline is satisfied by no overlap at all.

**What would make it load-bearing.** Make overlap a structural fact rather than a
duration. Have each mock record the arrival instant of every request, then assert the
two endpoints' arrival sequences **interleave** (some request to B arrives between two
requests to A). An interleave is impossible for a sequential implementation regardless
of machine speed, and it needs no timing threshold. If a timing form is kept, measure
the sequential baseline in the same test (`--concurrency 1` over the same two mocks)
and assert a ratio, so the threshold is not a guess about CI.

### I7. `two_endpoints_on_one_host_still_serialise` has no body and three ways to pass trivially.

> "same host, two endpoint paths, concurrency 2, a min gap set small but non-zero, and
> the server records arrival times. The two arrivals must be at least the gap apart.
> A timeout wraps it because a reentrancy mistake hangs."

Concretely, spell out: (a) it must be **one** `MockServer` with two paths. Two
`MockServer` instances are two `host_key`s, because `host_key` keeps a non-default port
(`politeness.rs`, `host_key`'s doc: "two engines commonly share a host on different
ports"), so the test would prove nothing about serialisation. (b) "the two arrivals"
is wrong: there are fourteen, seven per endpoint. Assert on **every consecutive pair
across both endpoints**, and assert non-overlap as well as spacing, since spacing
alone would hold for two requests that overlapped and released together. (c) Assert
that both endpoints produced a full row set, or a sweep that dropped one endpoint
passes. (d) Use the existing `prober/tests/common/mod.rs::without_deadlocking`
(20s, and its module docstring documents the 4m47s hang it was built for) rather than
an ad-hoc `tokio::time::timeout`. The plan never mentions this helper exists.

### I8. `concurrency_zero_is_rejected` is inconsistent with the validation the plan describes, and the implementation silently repairs 0 anyway.

> `let err = Args::try_parse_from([..., "--concurrency", "0"]).unwrap_err();`

> "Validate `>= 1` and reject 0 with a clear message"

> `let permits = Arc::new(Semaphore::new(concurrency.max(1)));`

Three positions, mutually inconsistent. If the check lives in `main()` beside
`validate_min_gap` (which is where the plan's prose points, and where the message can
name the relationship), then `try_parse_from` **succeeds** and `unwrap_err()` panics.
If the check is a clap `value_parser!(usize).range(1..)`, the test is right but the
"clear message" is clap's. And `concurrency.max(1)` inside the library silently
repairs a caller's 0 while main refuses it, which is the same silent default
`Politeness::unlimited()`'s doc comment refuses in its own words.

**What it should say.** Make `run_sweep` take `NonZeroUsize`, so 0 is not expressible,
delete the `.max(1)`, and put the validation in `main.rs` beside `validate_min_gap`
with C4's arithmetic in the message. Then test the validator directly, the way
`a_gap_that_cannot_fit_inside_the_metric_budget_is_refused` does, and drop the clap
test. (Note `Semaphore::new(0)` would hang, not fail, which is why `.max(1)` looked
attractive; a `NonZeroUsize` removes the hazard at the type level.)

### I9. The metrics-loader test fixture uses field names that do not exist, and its assertion cannot tell that apart from the failure it is testing for.

> ```
> id = "has:classes"
> title = "t"
> probe = "ask_data"
> cost = "cheap"
> ```
> `assert!(err.to_string().contains("id"), "unhelpful error: {err}");`

`MetricDef` has `label`, `dimension` and `kind`, not `title` and `probe`, and `kind`
values are PascalCase (`AskData`, not `ask_data`). See `prober/metrics.toml:5-11`.
So `load_metrics` rejects this input for a missing required field, long before it
looks at the colon, and `contains("id")` cannot distinguish "rejected the colon" from
"missing field `label`". The test would pass or fail for reasons unrelated to its
name, which is this project's recorded failure mode.

Also, the function is `load_metrics`, not `load_from_str`. The plan instructs "Match
the existing test helpers in each file rather than inventing new ones" and then
invents three (`load_from_str`, `subjects_of`, `emit_for`). Either write the calls
against the real names or state that the helpers are to be located first, but do not
ship a body that will not compile.

Fix the fixture to the real schema and assert on the specific message
(`contains("has:classes")` and a phrase naming what is allowed), so the assertion can
only be satisfied by the rejection it is named for.

### I10. Two of the five identifier tests are not load-bearing as written.

`a_subject_does_not_depend_on_where_its_row_sat` asserts only that reversing the input
list leaves endpoint a's subject unchanged, plus non-emptiness. It passes on an
implementation that passes the **metric id** where the endpoint belongs (both list
entries use `"cors"`), which is a plausible parameter-order mistake in a four-argument
function. Strengthen it to tie emit's output to the helper: assert the emitted subject
for (a, cors) equals `subject_iri(FactKind::Measurement, &run(), "https://a.example/sparql", "cors")`
exactly. That is the same technique the plan already prescribes for the three
hard-coded tests in Step 4, and it should be used here too.

`a_percent_encoded_endpoint_is_still_a_valid_iri` cannot fail. The encoder's output is
by construction only unreserved ASCII and `%HH`, so no input string can make
`NamedNode::new` reject it; and in `emit.rs` every fact loop validates the endpoint as
a `NamedNode` and `continue`s **before** the subject is built (`:224`, `:302`, `:402`),
so a junk endpoint never reaches `subject_iri` in the first place. To be load-bearing
it should pin the encoding itself: assert one exact expected IRI string, which fixes
uppercase hex, the unreserved set, and UTF-8-byte-wise encoding of the non-ASCII case.

`the_three_kinds_never_share_a_subject`, `two_endpoints_differing_only_in_an_escape...`
and `an_endpoint_cannot_shift_the_metric_field` are all genuinely falsifiable. Keep
them as they are.

### I11. Holding the permit across the politeness wait means adjacent same-host endpoints consume every permit and the sweep runs at 1x.

> "Held for the whole endpoint, not per request: the point is to bound how many
> endpoints are in flight. Per-request spacing is the politeness gate's job and it is
> untouched here."

> "Per-host politeness already serialises requests to one host, so concurrency only
> buys parallelism across different hosts"

The second sentence is true and the consequence is missing. Tasks are spawned in input
order and `tokio::sync::Semaphore` is FIFO, so the four in-flight endpoints are the
next four in the registry. A registry seeded from LOD Cloud plus YummyData is
clustered by publisher, so four consecutive same-host entries are the expected case,
not the exotic one. When that happens all four permits are held by endpoints that
serialise on one host lock, the other 544 make no progress, and the sweep runs at 1x
for that stretch. The plan claims a 4x speedup with no mention of this.

The fix is nearly free, and the plan's own design is what makes it free: because
subjects are now derived and results land in a slot indexed by input position,
**dispatch order is fully decoupled from output order**. Spawn in an order that
round-robins over `politeness::host_key` groups while keeping slot `i` as the input
position. Say that in the plan, and say that the "overlaps at all" test uses two
different hosts so it never exercises this case.

### I12. The plan never says which endpoint string goes into the subject, and the obvious "improvement" would silently merge two registry entries.

The brief's normalisation question has a right answer in this codebase and the plan
must state it: the subject must use the registry string **verbatim** - not lowercased,
not trailing-slash-normalised, and not the post-redirect `final_url`. Two reasons, both
already decided elsewhere: `dqv:computedOn` publishes the registry string
(`emit.rs:258`), so a normalised subject and its own `computedOn` would name the
endpoint two ways in one node; and `registry::dedupe` rules deliberately that
`http://x/sparql` and `http://X/sparql` are **two** registry entries
(`registry.rs:130-145`, `a_near_duplicate_is_two_entries_not_one`), so lowercasing
inside the encoder would merge two entries the registry keeps apart, which is the C3
collision arriving by the front door.

So `HTTP://A.example` and `http://a.example` get two subjects and one host bucket, and
that asymmetry is correct: the gate asks "which server must I not hammer", the subject
asks "which registry entry is this about". Write that down, and write "no normalisation
of any kind inside `subject_iri`" as a constraint, because an implementer handed the
word "normalisation" will reach for `to_ascii_lowercase`.

### I13. The identifier embeds a reversible endpoint URL forever, and the plan does not say so.

The plan argues correctly that no consumer needs to parse the IRI, but the relevant
property is not whether a consumer parses it, it is that anyone **can**. A registry
URL carrying userinfo (`http://user:pw@host/sparql`) or an API key in its query string
is published in every subject of every fact about it, in a graph the project's own
rules say is immutable and append-only. `politeness.rs`'s `host_key` already reasons
about userinfo ("Userinfo is credentials, not identity") but nothing refuses such a
URL. Stage 5 accepts public submissions, so this is a submission-time question, not a
hypothetical.

This does not change the choice; percent-encoding is still right, and the deciding
reason is the one the plan half-states: stage 1c-b4 needs a subject an endpoint's own
chunk can compute **locally**, which rules out every global-rank or sorted-index
scheme, not just hashing. (The plan's hash argument sets up a false dichotomy: the
alternative it never considers is an opaque run-local rank over sorted
(endpoint, metric), which is injective and short and leaks nothing, and which fails
only on chunk-locality. Saying that makes the trade-off legible; "std has no stable
hash" does not.) What the plan should add is the consequence and its mitigation:
reject a URL with userinfo at registry load, and state that the endpoint URL is a
permanent, reversible part of every subject.

### I14. The plan contradicts the spec's per-endpoint isolation requirement, and documents an order guarantee that stage 1c-b4 must break.

Spec, in the binding "Reliability and cost control" list:

> "**Per-endpoint isolation.** One endpoint's failure or slowness must never delay
> another's results or block the run from finalizing. Results are written per endpoint
> as they complete."

The plan's `run_sweep` returns only after the slowest task finishes and buffers the
whole `Sweep` in memory, so one endpoint burning its 600s budget delays the run's
entire output by up to 600s. That is the sequential loop's defect at a smaller
constant, and the spec forbids it in as many words. Where the plan contradicts the
spec, the spec wins.

It also creates a promise it is about to break. Task 4 instructs the README to state
"order: quads appear grouped by endpoint in input-list order", and 1c-b4's whole point
is writing each endpoint's chunk as it completes, which is completion order. So this
stage would publish a guarantee that next stage must retract.

**What the plan should say.** Scope the order property honestly: it holds for a
single-file emission, it exists so a `git diff` of two run files is readable, and it
is deliberately **not** a property of the graph (N-Quads order carries no meaning;
`web/load_run.py` inserts into Oxigraph, which is order-blind, so no real consumer
depends on it). Then say that the identity guarantee, not the order guarantee, is what
1c-b4 relies on, and that 1c-b4 is expected to emit chunks in completion order.

### I15. Every web-layer test stays on the old subject shape, and nothing tests the new one.

The plan is right that the nine fixtures remain valid and that only
`test_endpoint_content.py:111` names an old IRI. But the consequence it draws is
incomplete: after this stage, 100% of the web layer's coverage is against a subject
shape the prober can no longer produce, and a store in production will hold both
shapes for as long as history is kept. `web/tests/test_fixture.py` records that
`run-with-samples.nq` is "a REAL sweep, copied byte-for-byte", which will no longer be
reproducible.

Add one new-scheme fixture (a hand-built run in the new shape, documented in
`test_fixture.py`'s provenance list the way every other synthetic fixture is), loaded
beside an old-scheme run, and assert the queries return both. That is the only way the
"two schemes coexist" claim is tested rather than asserted.

### I16. Task 2 leaves behind two doc comments that the change makes false.

`lib.rs:37-45` (on `Sweep`) and `lib.rs:131-140` (on `probe_endpoint`) both exist
solely to justify the `&mut` mechanism: "`read` starts `false` and is set inside
`probe_endpoint` as soon as the fetch's `Declarations` are known", "appending as it
goes so a caller that cancels this future can still see how far it got", "a cancelled
future returns nothing". Task 2 says "Nothing else moves" and Task 4 only mentions the
independence claim, so both blocks survive unchanged and false. The plan's own Global
Constraint says "Every comment and doc sentence must be defensible by pointing at a
line of code. Seven sentences on the previous branch were not." Name these two blocks
in Task 2's steps.

### I17. "the measured cheap-sweep cost (roughly 14s per endpoint)" is not a measurement, is a floor, and ignores the failure path that motivates the whole stage.

> "at the measured cheap-sweep cost (roughly 14s per endpoint) it turns a 548-endpoint
> sweep from about 2h10m into about 32m, which is comfortably inside a daily schedule."

The arithmetic checks out (548 x 14.1 = 7727s = 2h09m; /4 = 1932s = 32m). Three things
are wrong around it.

1. It is not measured. `README.md:150-151`: "This is a rough estimate, not a
   measurement, because no full registry sweep has been run yet." The number is
   `(7 x 0.3) + 12`, built from an assumed 300ms latency. Calling it measured is
   exactly the kind of claim this project's reviews keep catching.
2. It is a **floor**, and the README says so, along with two caveats the plan drops:
   "This assumes all endpoints are distinct hosts" and "Request latencies also vary
   widely". Dividing a floor by four yields a floor, not an expected duration, so
   "comfortably inside a daily schedule" is not established by it.
3. It ignores the failure path, which is the reason 548 endpoints need this stage at
   all. A black-holed endpoint costs its full 600s endpoint budget. The real bound is
   `sum(per-endpoint cost) / concurrency`, worst case `548 x 600 / 4 = 22.8 hours`. At
   a plausible 10% dead-or-black-holed, `(493 x 14.1 + 55 x 600) / 4 = 4.0 hours`.

Say what the default is actually chosen for: politeness (aggregate outbound rate,
which at concurrency 4 with a 2s per-host gap is about 2 requests per second) and the
metric-budget relation in C4. Present the 32m as a floor with the failure path priced
in, or drop the schedule claim.

### I18. Task 3's signature change touches roughly twenty existing call sites the plan never mentions.

> "Produces: `pub async fn run_sweep(endpoints: &[String], defs: &[MetricDef], declined: &[MetricDef], client: Arc<Client>, budget: Budget, concurrency: usize) -> Sweep`. `main.rs` is the only caller."

`main.rs` is not the only caller. `prober/tests/end_to_end.rs` calls `run_sweep` at
about twenty places (`:52`, `:155`, `:180`, `:214`, `:246`, `:273`, `:311`, `:343`,
`:390`, `:441`, `:546`, `:611`, `:680`, `:734`, `:774`, `:818`, and more), every one
of them passing `&client` and no concurrency. Changing `&Client` to `Arc<Client>` and
adding a parameter is a mechanical edit to all of them, and Task 2's rule ("a refactor
that forces a test change is a behaviour change") will fire twenty times for a reason
that is not a behaviour change. Say so up front, say which concurrency value the
existing tests should pass (1, so they keep testing what they test today), and
consider a `client: &Arc<Client>` parameter so the edit is smaller. Otherwise the
executor is left deciding, twenty times, whether a required edit is the kind the plan
told them to be suspicious of.

## What is right and should not be relitigated

- Identifiers before the refactor before concurrency is the correct order, and the
  reasoning given for it is sound.
- Rejecting "byte-identical output" and replacing it with order plus identity is the
  right correction of the superseded plan's decisive defect 1.
- Percent-encoding over a hash is the right family of choice, for the chunk-locality
  reason (see I13), and the injectivity argument holds for every input I could
  construct.
- Validating the metric id at load is worth more than the plan claims: `emit.rs:267`
  already interpolates the raw id into `urn:sparqlwatch:metric:{id}`, so an id with a
  space makes `nn()` return `Err` and `main.rs` loses the **entire** run's output at
  the `?`. The validation closes a pre-existing whole-run-loss hazard. Say so.
- The read of the web layer is accurate: the queries match on predicates, the fixtures
  stay valid, and one Python constant needs updating.
- No new deadlock is introduced by concurrency plus the gate. I checked: `gated_hop`
  is the single `acquire`, it holds one host guard at a time and drops it before
  returning, a redirect chain re-acquires per hop rather than nesting, and
  `politeness.rs` carries a compile-time `_acquire_future_is_send` assertion that was
  added in anticipation of exactly this stage. `stand_down` under concurrency defers
  other endpoints on the host at their own `acquire`, bounded by each one's own
  endpoint budget, which is correct behaviour rather than a hazard. The plan's claim
  here stands; C4 and I11 are about budget and throughput, not deadlock.

Re-read the rewritten plan (751 lines) against the code and against the 28 findings
above. **26 of 28 are fully answered**, M4 is partially answered and M5 is unanswered
(both Minor, restated as N12). The four design reversals are correct: C1's diagnosis

endpoint on the `Err` arm; C3's helper-side metric-id check and duplicate guard are in
the right places; C4's validator sits beside `validate_min_gap` where it belongs. I
also spot-checked the plan's new citations: `registry.rs:130-145`, `README.md:148-151`,
`emit.rs:224/:258/:330/:540`, the 32 `end_to_end.rs` call sites, and the exact expected

## New Critical

### N1. `validate_concurrency`'s relation omits the dominant term. It certifies concurrency 4 as safe on a shared host when it is not, and no value of concurrency above 1 is safe there.

> ```
> (concurrency - 1) * min_gap + min_gap + request_budget < metric_budget
> ```
> "At the default: `3 * 2 + 2 + 30 = 38 < 60`, safe."

The model behind this is "a competitor holds the host lock for its gap". It does not.
`gated_hop` acquires the guard and holds it until the function returns, so a competitor
holds the lock for **its gap plus its whole request**, and on a throttled host for its
gap plus request plus the honoured `Retry-After` plus the retried request. `main.rs:46-63`
already states that hold time as arithmetic: "The wait happens inside the held per-host
guard, which sits inside the metric budget along with the gap, the first request and the
retried request", worst case `2 + 30 + 30 = 62`, and with the cap `2 + 30 + 20 + 30 = 82`.

So the worst-case wait for the host lock with `c` endpoints in flight on one host is
`(c - 1) x hold`, where `hold` is up to 82s, not `(c - 1) x min_gap = 6s`. At the
default of 4 that is up to 246 seconds of waiting inside a 60-second metric budget.
The plan's validator would accept it and print nothing. This is the third time this
project has published cap arithmetic that omits a term, and it is the same term the
retry-cap comment was written to catch.

The consequence is bounded (an expired metric budget reports `indeterminate`, which is
honest) but it is the exact failure `validate_min_gap`'s doc says must be refused up
front, because a cancelled metric budget is silent: "makes a healthy endpoint report
`indeterminate` almost everywhere, and nothing in a sweep warns about it". Concurrency
would convert "slow but measurable" into "indeterminate" for every host-clustered slow
server in the registry, and those are precisely the endpoints a quality monitor exists
to characterise.

Host-group round-robin dispatch (I11's fix, correctly adopted) does not bound this. It
spreads the *start* order, but endpoint durations range from 14s to 600s, so after the
first pass the in-flight set drifts and same-host co-residency recurs; and with a
registry whose 548 URLs sit on far fewer than 548 hosts, some co-residency is
unavoidable by counting alone.

**What the plan should say instead.** Make the invariant structural rather than
arithmetic: **one endpoint per host in flight**. Keep the global `Semaphore` for the
concurrency bound and add a per-`host_key` permit (a `HashMap<String, Arc<Semaphore>>`
of one permit each, or simply group the endpoint list by `host_key` and give each group
one sequential task, then bound the number of concurrent groups). Acquire the host
permit *before* the global permit, or acquire the host permit and skip to the next host
group, so a blocked host does not sit on a global permit either. Then:

- no endpoint ever waits on another endpoint's host lock, so the metric budget sees
  exactly what it sees today and `validate_concurrency` reduces to `validate_min_gap`'s
  existing relation with no new term;
- the plan's own sentence "concurrency only buys parallelism across different hosts"
  becomes true by construction rather than by hope;
- I11 is closed by a guarantee instead of a heuristic;
- `two_endpoints_on_one_host_still_serialise` becomes a test of a structural property.

If a per-host permit is rejected, then the relation must use `hold` rather than
`min_gap`, and the honest conclusion is that `c = 1` is the only value that satisfies it
at the shipped budgets. Say that rather than shipping a validator that passes 4.

## New Important

### N2. Arguing back on the duplicate-subject guard: skip-the-later publishes a confident answer where the data is contradictory.

> "The duplicate guard: keep a `HashSet` of subjects already emitted in this run and
> skip a repeat, warning with the endpoint, the metric and the verdict that is being
> dropped. Skip rather than refuse the whole emission, matching the junk-endpoint
> handling at `:224` and for the same reason stated there"

I agree with the half of the call that matters: refusing the whole emission after hours
of probing is wrong, and the junk-endpoint precedent is the right one to reach for. But
the precedent does not say "keep one of two conflicting facts"; it says **publish
nothing about the thing you cannot state correctly**, and record the loss in the log.
At `:224` a skipped row means the graph asserts nothing about that (endpoint, metric).
Here, skipping the later row means the graph asserts the earlier row's verdict as the
sole observation, with full confidence, having silently discarded an observation that
contradicted it. The plan's own test makes this concrete: it feeds `Verified` then
`Absent` and asserts one `dqv:value` survives, which means the graph will say
`verified` about a pair we also measured as `absent`. Both are assertive verdicts. That
is a confident wrong answer produced by the guard that exists to prevent one.

**What it should do instead.** Two passes, or one pass with a pre-scan: count subjects
first, then emit. A subject appearing once emits normally. A subject appearing more than
once emits **nothing** and logs at `warn` with the endpoint, the metric and every
verdict dropped, so the pair is absent from the graph (a shape `web/queries/*.rq`
already handles, since an endpoint with no measurement for a metric is a routine case)
and the log is the only place the contradiction lives. Keep the "skip, never abort"
decision and its junk-endpoint justification, which are right. If a cheaper single pass
is wanted: skip a repeat only when it is byte-identical to what was already emitted
(RDF is a set, so that is a genuine no-op), and treat a repeat that would differ as the
drop-the-whole-subject case. Update the test to assert **zero** `dqv:value` objects for
the conflicting pair, not one.

The `MetricId` newtype deferral, by contrast, I accept as stated: the invariant is now
enforced at both points that rely on it, both are tested, and the reason for deferring
is given. It is a stated trade-off, not an oversight.

### N3. `subject_iri`'s new metric-id rejection loses the entire run's output, contradicting the duplicate guard two paragraphs away.

`subject_iri` returns `anyhow::Result` and the three call sites use `?` (that is how
`nn()` is used throughout `emit.rs`). So a metric id containing a colon that reaches
emission makes `emit_nquads` return `Err`, and `main.rs:192-202` propagates it with `?`
**before** `std::fs::write`, so the whole sweep's output is discarded. That is the
outcome the same task's duplicate guard explicitly refuses ("aborting turns hours of
work into no output"), and the outcome `emit.rs:224` refuses for a junk endpoint. Two
guards in one function, opposite policies, no stated reason for the difference.

It is reachable: `load_metrics` refuses such an id, but `MetricDef` is `pub` with `pub`
fields and every integration test hand-builds one, so the guarantee is a convention, not
a type. Say that the metric-id failure is handled like the junk endpoint: skip the fact,
warn with the endpoint and the id, keep the rest of the run. Then `subject_iri`'s
`Result` is consumed at the call site rather than propagated, and the Done criterion
"refused by the loader **and** by `subject_iri`" still holds.

### N4. `only_the_subjects_changed` is the plan's central proof and is specified in a way that will produce either a parallel emitter or a weakened test.

> "(Keep a copy of the old `format!` shape inside the test, clearly named as the
> historical shape, so the comparison has something to compare to.)"

A copy of the old subject *format string* is not something to compare to. To emit under
the old scheme you need the old *emission walk*, including the running index, which
means duplicating `emit_nquads` inside the test, where it will rot immediately. And it
is unnecessary: the quantity being compared, the `(predicate, object)` multiset plus the
quad count, does not depend on subjects at all.

**What it should say.** Order the steps so the comparison is against a frozen artefact.
In Step 1, before any implementation, emit one synthesized `Sweep` with the **current**
code and freeze its sorted `(predicate, object)` multiset and quad count as an inline
`const` in the test, named as the pre-1c-b3 baseline with the date. In Step 4, assert
the new emission reproduces both exactly. That is decidable, needs no parallel emitter,
runs in CI, and is the strongest form of the "no predicate and no object changed"
Global Constraint.

### N5. `run_sweep -> (Sweep, usize)` invalidates the plan's own claim about the 32 call sites.

> "`&Arc<Client>` rather than `Arc<Client>` keeps the 32 existing call-site edits to
> adding `&` and a concurrency argument."

Every one of the 32 sites is a destructuring binding: `let Sweep { rows, declarations_read: _..., not_measured: _..., content_samples: _... } = without_deadlocking(run_sweep(...)).await;`
(see `end_to_end.rs:52`, `:155`, `:180`, and so on). Changing the return type to a
tuple forces every one of them to become `let (Sweep { .. }, _failed) = ...`, which is
not "adding `&` and a concurrency argument". The `&Arc<Client>` choice is good and worth
keeping; the claim attached to it is now false.

Better: keep `-> Sweep` and put the count on the struct as `pub failed_endpoints: usize`.
It belongs there on the merits (it is a fact about the run, alongside the four fact
lists, and N7 argues it should reach the graph), `main.rs` reads it after emission
exactly as planned, and the call-site edit really does reduce to `&` plus one argument.

### N6. There is a 33rd `run_sweep` call site the plan does not list, in a file that must still compile.

`prober/tests/live_smoke.rs` calls `run_sweep` once. Its tests are `#[ignore]`d, so the
suite shows "2 ignored" and the file is easy to miss, but `cargo test` compiles ignored
tests and CI runs `-D warnings`, so Task 3 leaves the build red until that site is
updated too. Add `prober/tests/live_smoke.rs` to the File Structure table and to Task 3's
file list, and say "32 in `end_to_end.rs` plus 1 in `live_smoke.rs`".

### N7. A panicked endpoint is indistinguishable in the graph from a budget expiry, and nothing published says the run is incomplete.

C2's fix is right and I am not relitigating it: routing through
`resolve(def, Declared { claimed: false }, Err(Expired))` keeps judgement in one place
and fills the slot. But it necessarily erases the distinction, because that is exactly
the call the ordinary expiry path makes. So a run in which the prober crashed on 30
endpoints looks, in the published graph, identical to a run in which 30 endpoints were
slow. The only record is the process exit status, which is not in the graph and is gone
by the time anyone queries it.

The spec's tier-3 rule is that a gap is a published fact rather than an inference, and
`NotMeasuredReason` exists precisely so a reason travels with the fact. Either add a
`NotMeasuredReason::ProberFailed` and emit one `NotMeasured` per metric for a failed
slot (which also keeps `resolve` out of a path where there was no observation at all),
or publish the count on the activity beside `urn:sparqlwatch:maxCost` as
`urn:sparqlwatch:failedEndpoints`. State which, and say in Task 5 that a consumer can
tell a complete run from an incomplete one.

### N8. Userinfo detection is unspecified, and the obvious implementation drops real endpoints.

> "Drops an endpoint whose URL carries userinfo, with a warning"

A `contains('@')` check drops `http://a.example/sparql?contact=x@y.example`, silently
removing a legitimate endpoint from every sweep. Userinfo is a property of the
**authority**, and `politeness::host_key` already parses it correctly: lowercase, strip
the scheme, take everything up to the first `/`, `?` or `#`, then `rfind('@')`. Specify
that the refusal reuses that parse (extract the shared step rather than writing a second
one), and add the negative test: a `@` in a path or query string is kept. Also state
that this changes what gets swept, so it belongs in the README's registry section
alongside the dedupe rule, not only in Known limitations.

### N9. `(493 x 14.1 + 55 x 600) / 4` is 2.8 hours, not 4.0.

> "at a plausible 10% dead `(493 * 14.1 + 55 * 600) / 4 = 4.0 hours`"

`(6951.3 + 33000) / 4 = 9987.8s = 2.77 hours`. The error is mine: the plan inherited it
verbatim from finding I17 above, where I wrote 4.0. The `548 * 600 / 4 = 22.8 hours`
worst case is correct, and so is `548 * 14.1 = 2h09m`. Correct the 10% figure to about
2.8 hours. Noted here rather than quietly fixed because a number that travelled from a
review into a plan without either party recomputing it is the same failure the plan is
trying to stop.

### N10. Task 4's fixture cannot be generated from a live sweep and still test what it is for.

> "Generate it with the Task 3 prober if the network allows, or hand-build it in the new
> shape."

The test is "an old-scheme and a new-scheme run for **the same endpoint** coexist, and
the most-recent-run selection picks the newer one". A live capture is about whatever the
registry holds at whatever time it ran, so it will not pair with `run-with-samples.nq`'s
endpoints and timestamps, and the most-recent-run assertions will have nothing to
compare. It is also not reproducible, which is why `test_fixture.py`'s provenance list
labels exactly one fixture as a real capture and every other as synthetic with its
construction written down.

Prescribe the construction that already exists: derive it from `run-with-samples.nq` by
rewriting the subjects into the new scheme and advancing the run IRI and
`prov:generatedAtTime`, which is precisely how `run-two-sweeps.nq` was built and
documented. Drop the "generate it with the prober" option.

## Verdict

Not yet safe to execute. N1 must be resolved first because it is a design decision

stated trade-off or a Minor.
