Two premises the plan does not state but which I verified, because the design
rests on them and a later reader will want them written down:

- **The last newline really is a statement boundary.** oxrdfio escapes a newline
  inside a literal (`Literal("a\nb")` serialises as `"a\\nb"`), so no emitted
  line can contain a raw newline, and no proper prefix of an N-Quads statement is
  itself a valid statement (the terminating `.` is always in the truncated part).
  So the "retry to the last newline" rule cannot silently change the meaning of
  a line. Say this in Task 2; it is the reason the rule is sound.
- **The activity quads are in the header, and every read query needs them.**
  `endpoint_measurements.rq`, `endpoint_content.rq` and `endpoint_description.rq`
  all require `?activity a prov:Activity ; prov:generatedAtTime ?generatedAt`
  inside the same graph. Header-first is therefore load-bearing, not tidy.

## Critical

### C1. Truncation happens at chunk granularity, not line granularity, and Task 2's line-level tolerance is what turns a half-written chunk into a published wrong fact.

> "Each chunk is one `write_all` of a buffer that ends in a newline, followed by
> a flush, so between chunks the file on disk is complete and valid."

> "A short write inside a single `write_all` can still leave a partial line. That
> is what Task 2 exists to survive, and the two halves together are the
> guarantee."

The two halves are not the guarantee. Dropping a partial *line* is safe. What a
mid-chunk death leaves is a partial *chunk*, and a partial chunk is a set of
complete, parseable, mutually inconsistent lines that Task 2 loads without a
murmur.

The concrete instance is the content sample. `emit.rs` writes a sample node in
this order: `rdf:type`, `sw:sampledFrom`, `sw:sampledBy`, `sw:sampleTruncated`,
`sw:sampleSize` (`:809-818`), then the `sw:sampledValue` lines (`:822`), then
`prov:wasGeneratedBy`. So a chunk cut anywhere inside the value list yields a
node asserting `sampleSize 200` and `sampleTruncated false` with three values
present. `endpoint_content.rq` does not require `prov:wasGeneratedBy` (its header
says so explicitly, because `run-truncated.nq` has none), so the node matches,
`endpoint_content.py` reads `size` from the graph and `classes` from the rows,
and `templates/endpoint.html:187` renders "200 classes sampled" above a list of
three, labelled "complete: not truncated". That is a confident wrong answer about
somebody's endpoint, in a graph the project's own rules say can never be
corrected. The emitter's comment at `emit.rs:698-701` states the invariant this
breaks: "the size is always verifiable from the graph itself".

It is not a theoretical window:

- A cut at a line boundary inside a chunk needs no partial write at all, and then
  Task 2's tolerance never even triggers (the file ends in a newline and parses),
  so the loader has no hook to refuse it.
- `Write::write_all` is documented to leave an unspecified number of bytes
  written when it returns `Err`. On `ENOSPC` it writes part of the chunk and then
  fails, which is exactly the path Task 3 describes as "Everything already
  written stays on disk and is loadable, which is the point of the stage." In the
  write-failure case that sentence is false.
- Chunks are not small. The committed `run-with-samples.nq` spends 19,692 bytes
  on 109 `sampledValue` lines; one endpoint's `classes` sample at the shipped
  `sample_limit` of 200 is roughly 40 KB, well over `BufWriter`'s 8 KB default
  capacity, so a `BufWriter` will issue several syscalls per chunk and a
  raw-`File` `write_all` will too.

**What the plan should say instead.** Make the chunk, not the line, the unit of
tolerance, and say so in both halves:

1. End every chunk with a single marker line that names the endpoint the chunk
   just completed (an `sw:` predicate on the activity, e.g.
   `<activity> sw:completedEndpoint <ep>`), written last.
2. Task 2's rule becomes: if the bytes do not parse, or the file does not end
   with a complete chunk, retry from the end of the last marker line; refuse
   anything else. A trailing group of complete-but-unterminated lines is
   discarded rather than loaded, which is the case this finding is about.
3. Size the writer's buffer so one chunk is one buffer, and state the largest
   chunk the shipped `metrics.toml` can produce so a reader can check the claim.

If the marker is rejected, the fallback is to move `sw:sampleSize` and
`sw:sampleTruncated` after the last `sw:sampledValue`, which closes this
particular instance and nothing else; a measurement row cut before its
`dqv:value` is already absent rather than wrong (the query needs both `dqv:value`
and `prov:wasGeneratedBy`), so the sample is the sharp edge, but "no fact family
may put its own summary before the things it summarises" is the rule worth
writing down.

### C2. The duplicate-subject guard is not a `HashSet`, and the guard the plan proposes to carry across chunks silently reverts the resolution stage 1c-b3 was rewritten for.

> "**The duplicate-subject guard** is currently one `HashSet` over the whole
> emission. Chunking would silently shrink its scope to a chunk. [...] So the set
> lives in `EmitState` and persists across chunks, and a comment says why."

Read `emit.rs:418-446`. The guard is two-phase: a `BTreeMap<subject, BTreeSet<payload>>`
pre-scan over all four fact lists, then `conflicted()` (`:233`), and a subject
whose payloads disagree **publishes nothing at all** (`:481-489`, `:753-761`).
The `emitted: BTreeSet<String>` at `:446` is a separate, secondary thing that
skips a *byte-identical* repeat only, and its comment says exactly that:
"so a byte-identical repeat is written once". Stage 1c-b3's review (N2) forced
this design in place of skip-the-later, on the ground that keeping the earlier of
two contradictory observations "will say `verified` about a pair we also measured
as `absent`. [...] That is a confident wrong answer produced by the guard that
exists to prevent one." The spec records the outcome at `:405`: "a repeated
(endpoint, metric) with conflicting facts publishes **nothing** about that pair
rather than a contradiction."

A pre-scan cannot persist across chunks, because chunk 1 is on disk before chunk
2 exists. So "the set lives in `EmitState` and persists across chunks" can only
mean the `emitted` set, i.e. skip-the-later, i.e. publish the first verdict with
full confidence and drop a contradicting observation without a trace in the
graph. In an append-only file it cannot be otherwise.

The plan's own escape clause does not hold either:

> "Within one endpoint that is still complete for the conflicting-pair case,
> because a (endpoint, metric) pair can only appear in its own endpoint's chunk,
> **but only as long as an endpoint appears in exactly one chunk**.
> `registry::dedupe` is what makes that true"

`dedupe` runs inside `load_endpoints`, called from `main.rs:186`. It is not on
the path the new writer sits on: `run_sweep` is `pub`, takes `&[String]`
unchecked, and 39 test call sites feed it hand-built lists (38 in
`prober/tests/end_to_end.rs`, 1 in `prober/tests/live_smoke.rs`);
`RunWriter::write_endpoint` will be `pub` too and its own unit tests will call it
directly. Today the pre-scan is a real backstop for all of those. Under chunking
it is not.

**What the plan should say instead.** (a) Describe the current guard correctly:
a payload pre-scan that publishes nothing on conflict, plus a byte-identical-repeat
skip. (b) Keep the pre-scan, scoped to one chunk, and state that it is complete
*because* an endpoint's facts are all in one chunk. (c) Make that a checked
invariant rather than an inherited convention: the only thing `EmitState` carries
across chunks is the set of endpoints already written, and `write_endpoint`
**refuses** a second chunk for an endpoint it has already written (error, or drop
with a warning naming the endpoint, matching `emit.rs:454`'s junk-endpoint
handling), because refusing is the only thing a writer can still do once the
earlier chunk is on disk. (d) Say that `EmitState` may hold nothing else that
makes a later chunk depend on an earlier one, which also settles the
`typed_endpoints` trap the plan raises two paragraphs earlier and then
contradicts: `typed_endpoints` must be per chunk, so every chunk types its own
endpoint.

### C3. Task 3's drain loop as specified hangs, and the plan's own warning does not name the requirement that prevents it.

> "the drain loop `recv()`s until the channel closes (every sender dropped), and
> the `JoinSet` is then joined to detect panics. Whatever shape you choose, **it
> must not deadlock**"

`tokio::sync::mpsc::channel` gives the caller a `Sender`. `run_sweep` clones it
into each spawned group and then, unless it drops its own copy before entering
the loop, holds a live sender for the whole loop, so `recv()` never returns
`None` and the sweep hangs after the last group finishes. This is the single most
common way to write this shape wrong, the plan chose the shape, and the plan does
not say who owns the senders. The codebase's history here is not neutral: the
politeness reentrancy hang cost 4m47s of CI and produced
`prober/tests/common/mod.rs::without_deadlocking`, which the plan again does not
mention while saying "put a timeout on any test that could hang".

Three more mechanics in the same paragraph need pinning, for the same reason:

- **Who sends, and what a failed send means.** When the drain loop returns early
  (C1's write failure, or the `?` on a chunk error), the receiver drops and every
  in-flight `send` returns `Err`. The existing code reaches for
  `.expect("the sweep owns this semaphore and never closes it")` in the analogous
  place (`lib.rs:232`), and an `.expect()` here converts a write failure into a
  panic per group, which then re-enters the panic path and writes
  `prober-failed` facts about endpoints that were measured. Say: a send error
  means the sweep is over, so the task returns quietly.
- **Bounded versus unbounded.** The plan asks for a justification and gives none.
  Bounded is safe here *because* the drain loop is not doing the probing: a
  blocked `send` holds its group's semaphore permit, which delays that host's
  next endpoint but cannot deadlock while the receiver is live. Bounded also
  bounds memory, which is the argument at 548 endpoints. Say that, and say the
  capacity.
- **Ordering of panic detection against the footer.** The footer must be written
  after the panic sweep, and the `prober-failed` chunks after the last real chunk,
  or a footer certifies a run whose failed endpoints are not yet in the file.
  With `covering` (`lib.rs:182`) plus the set of endpoints already written, the
  plan's "work out which endpoints of a panicked group never arrived" is
  implementable, but say the order explicitly.

### C4. `assemble` disappears and nothing in the plan builds the per-endpoint `cost-ceiling` facts, so a complete default run loses the only fact it publishes about `classes`.

> "`run_sweep` takes `&mut RunWriter` and returns whatever the caller still needs
> (the failure count at least). It no longer accumulates the four fact lists for
> the caller to emit."

`assemble` (`lib.rs:266-321`) does three things, not one. It reassembles by slot,
it fills a failed slot with `ProberFailed` facts, and it appends one
`NotMeasured { reason: CostCeiling }` per (endpoint, declined metric) **for every
endpoint, measured or failed** (`:311-319`). `declined` is a parameter of
`run_sweep` and lives nowhere else; `EndpointSweep` (`lib.rs:323` onward) does not
carry it. The plan never mentions `declined`, never defines `EndpointFacts`, and
the natural reading of "send each endpoint's `EndpointSweep` over a channel and
write it" drops the cost-ceiling family entirely.

That is not a cosmetic loss. Under the default `--max-cost cheap`, `classes` is
declined, so its `NotMeasured` fact is the **only** thing a default run says
about class content, and `README.md:530-534` and `app.py:558-562` both hang their
honesty on it: without it, `_declined_classes` returns `None` and the page falls
back to "this run recorded no measurement of the classes metric either", which is
a different and weaker claim than "we chose not to look". The spec's tier rule
(`:168`, `:173`) requires the fact. It also breaks the plan's own Global
Constraint that a completed run's published quads do not change, and it would
pass every test that only inspects measurements.

**What the plan should say instead.** Define `EndpointFacts` explicitly as one
endpoint's rows, its `declarationsRead`, its `NotMeasured` facts (both families)
and its samples, and say who builds it: either the group task appends the
declined facts before sending, or the drain loop does so on receipt, with
`declined` still passed to `run_sweep` and still never interpreted there. Then
say what happens to `assemble` (deleted, or kept as the per-endpoint builder and
renamed) and what happens to
`a_failed_group_still_carries_facts_for_every_endpoint_in_it`, which is
`assemble`'s only unit test and the only unit-level pin on the `ProberFailed`
contract.

### C5. `RunWriter::new` truncates `--out` at t=0, so a crashed sweep now destroys the previous run's file. That file is the project's source of truth and cannot be re-observed.

> "`RunWriter::new(path, RunHeader) -> io::Result<RunWriter>` (opens, truncates,
> writes the header)"

Today `main.rs:203` calls `std::fs::write` once, at the end, so a sweep that dies
at endpoint 500 leaves the previous run's `--out` file untouched. After this
change the file is truncated before the first request goes out, and a crash
leaves a partial run where a complete one was. The documented workflow reuses one
path (`prober/README.md:69` and `:779`: `--out run.nq`; `web/README.md:74` loads
`path/to/run.nq`), and `--out` defaults to `run.nq`, so this is the ordinary
invocation and not an exotic one.

The loss is unrecoverable in the way that matters for a monitor.
`web/load_run.py`'s docstring is explicit that the layering runs the other way:
"the store is a derived artefact. The .nq files the prober writes are the source
of truth". And a sweep is an observation of a changing world at a given `--at`;
`README.md:597-601` already says two runs of one `--at` differ in `elapsedMs` and
can differ in verdicts. Nothing re-creates last night's file.

**What the plan should say instead.** Write to a sibling path
(`<out>.partial`, or `<out>.<pid>`) and `rename` onto `--out` in
`RunWriter::finish`. `rename` within a directory is atomic on macOS and Linux, so
`--out` is always either the previous complete run or this one, a crash leaves
the partial file under its own name where `load_run.py` can still take it, and
the stage's goal is fully met. Document the partial file's name in the README
beside the guarantee, and add a test that a crashed sweep leaves the previous
`--out` intact.

## Important

### I1. The plan shrinks `Sweep` without mentioning the 39 call sites and two order tests that read it, including the only tests that pin this stage's own contracts.

`prober/tests/end_to_end.rs` calls `run_sweep` 38 times and destructures `Sweep`
38 times, with 110 references to `rows` and 114 to the other three lists;
`prober/tests/live_smoke.rs` adds one (`#[ignore]`d, still compiled under
`-D warnings`). Neither file appears in the plan's File Structure table, and Task
3's file list says only "Test: `prober/tests/`". Two of those tests are about
this stage directly and are not mentioned anywhere in the plan:
`output_order_is_input_order_not_completion_order` (`end_to_end.rs:2216`), which
this stage must delete or invert, and
`a_panicked_group_publishes_prober_failed_for_every_endpoint_it_held`
(`:2476`), whose assertions are a `Vec` equality in input order (`:2551-2568`).

The cheap resolution is to keep `Sweep` whole: the drain loop can accumulate the
four lists as it writes them and return them, which keeps 39 call sites and every
existing fact-level assertion compiling and meaningful, keeps `main.rs:205-209`'s
log line (which reads `rows.len()`, `not_measured.len()` and
`content_samples.len()`), and reduces this stage's edit to *where the bytes go*.
If `Sweep` really must shrink, then say so, say that roughly 220 assertions move
to reading the file the writer produced, and put that work in its own commit so
the behaviour change is attributable. Either way, name the two order tests and
say what becomes of them.

### I2. Task 1 mandates two new published quads while the Global Constraints forbid any, and the test the project uses to guard the data model is built to fail on exactly that.

> "**This stage must change no published quad** for a run that completes."

> "The header publishes one quad promising that this run will be finalised [...]
> The footer carries `failedEndpoints` and a finalisation timestamp."

> "Every existing emit test passes untouched, including `only_the_subjects_changed`.
> If any needed editing, say why: this task is supposed to change nothing a run
> publishes."

`only_the_subjects_changed` (`emit.rs:1017`) freezes the exact sorted
`(predicate, object)` multiset and the exact count, and its own comment refuses
the loophole: "The baseline is not weakened to tolerate additions, because its
whole value is that an unintended predicate cannot slip in; an intended one costs
this paragraph." Adding the promise quad and the finalisation timestamp takes the
count from 43 to 45 and the test goes red. An executor handed three mutually
exclusive instructions will either weaken the project's central data-model guard
or quietly drop the header quad.

Worse for the timestamp: `RunEmission`'s doc (`emit.rs:271-274`) states that
`emit_nquads` "reads no clock, no environment and no global, so the same inputs
always produce the same document", and a finalisation instant is a clock read
that cannot be frozen in a baseline at all.

**What the plan should say.** Replace the constraint with what is actually
intended: no quad about an endpoint, a metric or a measurement changes; the
activity gains exactly two run-level facts, named, and the baseline moves with
the paragraph the test's comment demands. Make the finalisation instant a
parameter of `RunFooter` supplied by `main.rs` (never read inside `emit`), and
say whether it is excluded from the baseline or frozen through a fixed value in
the test.

### I3. The equality test becomes a tautology the moment Task 1 Step 3 lands, so it proves nothing after the change it exists to police.

> "Assert that emit_header + each emit_endpoint + emit_footer, concatenated,
> parses to exactly the same SET of quads as emit_nquads over the same input."

> "`emit_nquads` becomes the composition"

After Step 3 both sides of the assertion are the same code path, so the test can
never fail again, and it will not catch a later change to the split. The project
already solved this exact problem the right way one stage ago:
`only_the_subjects_changed` freezes a baseline as an inline `const` with the date
it was taken. Do the same here: in Step 1, before touching anything, emit the
synthesized run with today's `emit_nquads` and freeze the sorted
`(predicate, object)` multiset and the count as a named baseline; in Step 4,
assert the composition reproduces it. That is decidable, survives Step 3, and
runs in CI.

### I4. "Footer present" is not a well-defined predicate, and the header quad asserts a future in a graph that can never be corrected.

> "header present, footer present: a complete run. header promise present, footer
> absent: **the run did not finish**"

The footer is described as two quads. A process killed midway through writing
them leaves one, and "footer present" then depends on which one a consumer looked
for. Nominate a single finalisation quad, require it to be the last line the
writer ever writes, and say that `failedEndpoints` is only trustworthy in the
presence of that marker.

Second, "one quad promising that this run will be finalised" is a claim about the
future published at t=0 into an immutable graph. If the run dies, the graph
permanently asserts something false, which is the shape of mistake this project's
governing rule exists to prevent. Publish a fact that is true when it is written:
the header says *how* this run is being written (`sw:emission "incremental"`),
the footer says *that* it finished and when (`prov:endedAtTime` is the standard
PROV predicate for exactly this and costs nothing to reuse). Then the three cases
read off two facts that were each true at the moment they were written, and
"unfinished" is an inference a consumer draws rather than a promise the graph
broke.

I checked the two load-order cases the brief raises and they are sound, so do not
change them: `load_run.py` replaces the graph wholesale, so loading a truncated
run and later the same run's complete file leaves the complete one, and a run
loaded twice is idempotent. Worth one sentence in the README, since it is the
non-obvious half of the design working in your favour.

### I5. Task 2 does not say where the tolerance lives, and the obvious placement leaves the plan's own reproduction case still failing.

`main()` validates every input file with `_parsed_graphs(data)` at
`load_run.py:200`, *before* `Store()` is constructed, and `load_run()` then calls
`_parsed_graphs` again at `:147`. So a tolerance implemented in `load_run()` is
never reached by the CLI: `python web/load_run.py store.db partial.nq`, the exact
command in the plan's measurement, still raises from line 200. Say that the
tolerance belongs in `_parsed_graphs`, that both callers therefore get it, and
that the warning must not be printed twice for one file (main parses each file
twice by design).

While there: `load_run.py` imports no logging and reports through `print` in
`main`. "log a warning" is unimplementable as written and untestable as
specified. Return the discarded byte count on `LoadResult`, print it in `main`
beside the existing "loaded N quads" line, and have the test assert on the
returned value rather than on captured output.

### I6. The tolerance rule does the wrong thing on a file with no newline at all: it reports loading zero quads and then refuses with an unrelated message.

> "If parsing fails **and** the input does not end in a newline, retry with
> everything up to and including the last newline."

I ran the cases. A file that is entirely one truncated line
(`<urn:s> <urn:p> <urn:`) fails to parse, has no trailing newline, and
`rfind(b"\n") + 1 == 0`, so the retry parses `b""` successfully to zero quads.
The warning then says 21 bytes discarded and 0 quads loaded, and
`_parsed_graphs` raises `input names no graphs; nothing to load` -- a true
sentence that misdiagnoses the file and buries the real error, which was the
truncation. Say: no newline in the input at all means refuse with the original
parse error, never a zero-quad "success" path.

The other enumerated inputs behave correctly and are worth recording so nobody
re-derives them: an empty file parses to zero quads and is already refused as
"names no graphs" (unchanged); a comments-only file likewise; a trailing comment
with no newline parses fine, so no tolerance triggers; CRLF parses; a middle-line
corruption is reported at the middle line, and dropping the last line cannot
rescue it, so the refuse-everything branch is right for the right reason. And, as
noted at the top, no truncated prefix of an emitted line can parse as a valid
statement, so the syntactic condition is sufficient here -- but that is a
property of oxrdfio's escaping, so write it down rather than leaving it lucky.

One case the plan should own out loud: a hand-edited file whose last line is
corrupt *and* which lacks a trailing newline is indistinguishable from a
truncated one and will be tolerated. That is inherent in the rule, it is the
right trade, and saying so is cheaper than a reviewer finding it later.

### I7. Task 4's derivation cannot see the endpoints a crash actually harmed.

> "One sentence, derived from the footer's absence on a run whose header promised
> one"

`endpoint_measurements.rq` picks the most recent run that recorded *anything for
this endpoint*. An endpoint the crashed run never reached has no facts in that
run, so the page shows the previous, finished run and the derivation above never
fires: the reader sees last night's verdicts with no hint that tonight's sweep
died before reaching this endpoint. Today that endpoint would carry
`prober-failed` facts in the newest run and the page would say "not measured", so
this is a regression in exactly the population the stage exists for. The
mitigation the page already has is real but thin: the header and the sub-line
date the run (`templates/endpoint.html:107`, `:113`), so nothing is undated.

The read tier can detect the case, and the honest derivation is two conditions,
not one: (a) the run whose facts I am showing did not finish; or (b) a newer run
exists, it did not finish, and it holds nothing for this endpoint. Say both, and
say which sentence each produces. (b) is what the crash produces at scale.

### I8. Task 4's file list omits the query layer and the RDF representation, so the two representations of the resource would disagree.

The unfinished flag is a fact in the run graph, and the page reads facts through
`web/queries/*.rq`: `endpoint_measurements.rq` selects the activity, and
`endpoint_measurements.py`'s `EndpointMeasurements` is the dataclass `app.py`
renders. Neither is in the plan's list. Nor is `endpoint_description.rq`, the
CONSTRUCT behind the RDF representation, whose own header states the invariant
this would break: "the HTML representation is built from those two queries and
the two representations must agree". Stage 3-1's spec row claims "the HTML and
the RDF agreeing on every verdict the run recorded". Add
`web/queries/endpoint_measurements.rq`, `web/endpoint_measurements.py` and
`web/queries/endpoint_description.rq`, and add the negotiation test that both
representations carry it.

### I9. `a_write_failure_stops_the_sweep_and_says_so` cannot be written against the interface the plan specifies.

> "`RunWriter::new(path, RunHeader) -> io::Result<RunWriter>`"

> "A writer over a path that cannot be written. Assert the error names the path
> and that what was already written is untouched."

An unwritable path fails in `new`, before the header and before any chunk, so the
test exercises the constructor and its second assertion is vacuous: nothing had
been written. The failure that matters is a chunk write failing partway through a
sweep, and with a `path` in the constructor there is no way to inject it. Make
`RunWriter` generic over `io::Write` (or add a `with_writer` constructor) so a
test can supply a writer that fails on the third chunk, and then the test can
assert what the plan actually wants: the sweep stops, the error names the path,
and the chunks already written are intact. Note that this is also the test that
would have caught C1's `ENOSPC` partial chunk.

### I10. `every_endpoint_is_written_as_it_finishes_not_at_the_end` has no mechanism, and the obvious implementation cannot fail.

> "Assert the file already contains the first endpoint's facts BEFORE the sweep
> returns."

Reading the file after awaiting `run_sweep` passes on a buffer-and-write-once
implementation, which is the thing this test exists to exclude. Specify the
mechanism: drive the sweep as a spawned task, poll the file (or a barrier the
slow mock releases) until the fast endpoint's chunk appears, and only then let
the slow endpoint answer, all inside `without_deadlocking`. Also say which mock
does the blocking, because with host grouping the two endpoints must be on
different hosts for the fast one to finish at all.

### I11. `a_sweep_killed_partway_leaves_a_loadable_file_of_what_it_finished` tests cancellation, not a crash, and the plan should say which of the two it proves.

> "abandon the sweep partway (drop the future, or abort the JoinSet)"

Dropping a future runs destructors; `SIGKILL` does not. The difference is exactly
the one that matters if the implementation buffers: a dropped future can flush on
drop and a killed process cannot. State that this test covers cancellation and
that Step 4's manual `SIGKILL` is the only check of the crash claim -- or, better,
make the buffering strategy explicit (flush at the end of every chunk, buffer
capacity at least one chunk) so both cases have the same worst case, and say that
`Drop` on the writer must not be relied on for correctness.

### I12. The `fsync` disclaimer's justification is false, and it is scheduled to be copied into the README.

> "since the .nq file is a derived artefact that a re-run reproduces"

`web/load_run.py`'s module docstring says the opposite, and it is the one that is

differ in verdict. So a lost run is not reproducible, it is gone.

The decision to skip `fsync` may still be correct, and the honest reasons are
available: a lost run is a gap in history rather than a false fact, the next
scheduled sweep restores coverage, and 548 `fsync` calls have an unmeasured cost.
Say that instead. Also say what an un-`fsync`ed file can look like after a power
loss, since it is not only truncation: a delayed-allocation filesystem can leave
a zeroed tail, which neither the line rule nor C1's chunk rule can rescue, and
the file is then refused whole. That is the honest boundary of the guarantee.

### I13. The README correction is scoped too narrowly: the order paragraph names mechanisms this stage deletes, as well as the property it abandons.

> "correct the input-order claim stage 1c-b3 wrote"

`README.md:590-596` says more than "input order". It says "each endpoint keeps

Also in the README: `failedEndpoints` moving to the footer invalidates
`README.md:376-378` (which the plan spots) *and* `emit.rs:293-297`, the field's

### I14. Task 1 never says how `emit_nquads` derives its chunks, which is the only non-trivial part of the split.

`emit_nquads` receives four flat lists and no endpoint order. To become "header
plus one chunk per endpoint plus footer" it must derive the endpoint sequence

## New Critical

### N1. The truncation rule strips the footer from every complete run, so the read tier would tell every visitor that every finished sweep did not finish.

> "A file that ends in a newline and parses but has no trailing marker is a run whose last
> chunk is incomplete: drop it."

A complete run's last line is not a chunk marker. Task 1 nominates
`<activity> prov:endedAtTime` as "the last line the writer ever writes", and the footer's
`failedEndpoints` line sits between the last marker and it. So on every complete file this
rule finds no trailing marker, truncates back to the last one, and discards both footer
quads. Task 4's condition (a) then fires on every page and every RDF representation:
"emission present, `endedAtTime` absent" is exactly the unfinished case. That is a confident
wrong answer about every run the project ever publishes, produced by the tolerance built to
prevent one, and Task 2's test list cannot catch it: it has a case for a truncated chunk, a
mid-file syntax error, a missing marker and an empty file, and no case that loads a
**complete** file and asserts the footer survived.

**What the plan should say.** The terminator set has more than one member. A file is
loadable as far as it goes if its last statement is a chunk marker **or** the footer's
`prov:endedAtTime`; truncate to whichever of the two occurs later; and add
`test_a_complete_file_loads_with_its_footer_and_the_same_quad_count` to Step 1's list. While
there, add the header's last line as a third terminator (see N11), so the three README cases
are all actually reachable.

### N2. Nothing in the crate can produce the finalisation instant, and the constraint that forbids `emit` a clock plus the one that forbids new dependencies leaves no stated way to get one.

> "`emit` reads **no clock** [...] so the finalisation instant is a parameter supplied by
> `main.rs`."

> "**No new dependencies.**"

`main.rs` reads no clock today, by design: `--at` is passed in "so runs are reproducible"
(`main.rs:23`), and `validate_instant` only validates a string it is handed. There is no
`chrono`, `time`, `humantime`, `jiff` or `iso8601` anywhere in `prober/Cargo.lock` (I
grepped all 246 packages), and `std` cannot format a `SystemTime` as `xsd:dateTime`. So the
plan mandates a fact it provides no sound way to produce, and the improvisation it invites is
hand-rolled civil-time arithmetic from Unix seconds, publishing its result as a typed
`xsd:dateTime` literal into a graph that is never rewritten. A leap-year or month-length
mistake there is a permanently wrong literal, and `emit` will not catch it: `nn()` validates
IRIs, not literal lexical spaces.

**Pick one in the plan, and say which.** (a) A `--ended-at` flag validated by the existing
`validate_instant`, supplied by whatever invokes the prober, exactly as `--at` already is.
This keeps `main.rs` clock-free, keeps the whole pipeline reproducible, reuses a validator
that already has a 12-case rejection test, and needs no dependency; the cron gets one more
`date -u` interpolation. (b) Hand-roll `SystemTime` to RFC 3339, as its own step with its own
table-driven test across a leap year and a month boundary, and say in the plan that this is a
step rather than a detail. (c) Drop the instant: make the footer a bare
`<activity> sw:finalised "true"^^xsd:boolean`, lose the PROV predicate, keep the marker
semantics. My recommendation is (a): it is the choice this project already made once, for the
same reason, one field over.

## New Important

### N3. "The activity gains exactly three run-level facts" is the wrong arithmetic, and Step 4 asserts it.

`sw:completedEndpoint` is one quad **per endpoint**, not one run-level fact, and
`failedEndpoints` moves without changing the count. For the fixture behind

### N4. Task 3 promises the returned `Sweep` in input order and builds it in completion order.

> "The drain loop accumulates the four lists as it writes them"

> "invert it into a test that the file is in completion order and that the returned `Sweep`
> is still in input order, which is the honest split."

Accumulating on arrival is completion order. Both halves are available and the existing code
already carries the mechanism: the group task sends `(slot, EndpointSweep)`, the drain loop
writes the chunk on receipt and stores into `slots[slot]`, and the `Sweep` is built by
walking the slots in input order after the loop, which is what `assemble` does today
(`lib.rs:266-321`). Without that, the panic test's `not_measured` `Vec` equality

and the plan's own claim that this stage's edit reduces to "where the bytes go" stops being
true. Say that slots survive, and say they are the reason the input-order half is still
assertable at all.

### N5. The marker must be matched structurally, not as a byte substring, or third-party data can spoof it.

`sw:sampledValue` objects are IRIs an endpoint returned, published verbatim
(`emit.rs:822`), and `urn:sparqlwatch:completedEndpoint` is a legal IRI for an endpoint to
return as a class. A loader that finds "the last chunk marker line" by scanning bytes for the
predicate will match
`<sample> <urn:sparqlwatch:sampledValue> <urn:sparqlwatch:completedEndpoint> <graph> .`
inside the incomplete final chunk and keep the partial chunk, which is the C1 failure arriving
through the front door. The project already reasons about exactly which values a third party
controls, in `web/tests/fixtures/run-hostile-literals.nq`'s docstring; that fixture's argument
("an IRI cannot contain `<`, `>` or `"`") does not help here, because the spoof needs none of
those characters.

Specify the match: iterate lines from the end and accept one only if parsing that single line
yields a statement whose **predicate** is the marker (or `prov:endedAtTime`), never a
substring test. Add the hostile case to Step 1's list, beside the truncated-at-a-line-boundary
case.

### N6. Task 4's condition (b) is an absence, and a CONSTRUCT can only emit presence, so the two representations will diverge unless the plan says what the RDF says.

> "the CONSTRUCT carries it too, and a negotiation test asserts both"

Condition (a) is expressible: the shown run's activity has `sw:emission` and no
`prov:endedAtTime`, and the CONSTRUCT can emit both facts it does have. Condition (b) is "a
newer run exists, did not finish, and has no `sw:completedEndpoint` for this endpoint", which
is two negations; a CONSTRUCT template cannot emit "no marker exists". So say what triples the
RDF representation emits for (b): the newer activity's own `sw:emission` and
`prov:generatedAtTime`, with the two negations expressed in the WHERE clause, so a client
holding the document can draw the same conclusion the page draws. Otherwise the negotiation
test will be written against whichever representation was built first, and
`endpoint_description.rq`'s header ("the two representations must agree") plus the spec's
stage 3-1 row are both broken by a stage whose Task 4 exists to prevent exactly that.

### N7. `emit_nquads` cannot keep its signature, and 41 construction sites move.

> "`emit_nquads` keeps its signature and becomes the composition, so every existing caller
> and test is unaffected."

`RunFooter` carries the finalisation instant and `RunEmission` has no field for it, so
`emit_nquads` cannot build a footer without gaining one (it may not read a clock, per the
same plan). Adding a field touches **41 struct literals**: 28 in `emit.rs` and 13 in
`prober/tests/end_to_end.rs`. That is mechanical and fine, and it is exactly the kind of edit
the previous stage's review asked to be counted in advance rather than discovered 41 times.
Say the number, say it is mechanical, and delete the claim that every existing test is
unaffected.

### N8. `<out>.partial` is a fixed name, so the next scheduled sweep destroys the previous crash's partial run. That is C5 displaced by one run.

The documented workflow is a fixed `--out run.nq` (`prober/README.md:69`, `:779`) on a daily
schedule, so: crash at 22:00 leaves `run.nq.partial`; the 23:00 sweep opens the same name and
truncates it before its first request. The 499 endpoints C5 exists to preserve are gone unless
someone loaded them within the hour, and nothing warns. `--at` is required and validated, so
